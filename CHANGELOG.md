# Changelog

Datahike releases continuously: every merge to `main` produces a new version `0.{minor}.{commit-count}` and a Clojars release. The complete change feed is the [git log](https://github.com/replikativ/datahike/commits/main); this file highlights **user-facing** changes — new features, stability transitions, breaking changes, deprecations, and notable fixes. Internal refactors, CI tweaks, dep bumps, and test-only changes are intentionally omitted.

When something is added, it's typically marked *Experimental*. When the API contract solidifies, a separate **Status changes** entry records the promotion (with the version it happened in).

## 0.8

- **`metrics` is cheap on a large database.** Per-attribute counts (and the
  AVET and history counts derived from them) come from the indices' subtree
  counts — one O(log n) `count-slice` per attribute — instead of a walk over
  every datom. `:per-entity-counts`, which is inherently a full walk with one
  map entry per entity, is no longer returned by default; ask for it with
  `(metrics db {:per-entity-counts? true})`. **Status change:** the key is
  optional in `SMetrics` now.
- **The HTTP API is embeddable.** *Experimental.* `datahike.http.routes/handler`
  returns the server's routes as a Ring handler for mounting inside a host
  application, under a prefix, sharing the host's connection registry
  (`:connections`), with the token checked and the body capped *before*
  anything is decoded. `datahike.http.server` is now a thin shell around it.
  See [doc/http-routes.md](doc/http-routes.md).
  **Breaking for embedders of the server namespace:** `datahike.http.server/app`
  now takes `(app config connections)`; `start-server`/`stop-server`/`-main`
  are unchanged, and `stop-server` now releases the databases the server
  opened. The `:datahike-server` writer no longer sends its token in request
  bodies, fails writer operations the server does not implement by name
  instead of with a 404, and returns database handles that can make remote
  calls.
  **The HTTP client now defaults to CBOR** (`:format :cbor` in the remote
  peer); pass `:format :transit`, `:edn` or `:json` to keep the old wire
  format.

- **Index warming is unified across the stack, and real on ClojureScript.**
  The breadth-first walk moved to persistent-sorted-set (>= 0.5.142), where
  every consumer shares it; `datahike.index.persistent-set.warm` is now the
  adapter (option dialect, clamp warning, and the adaptation of PSS's async
  shapes to datahike's channel convention — including the ClojureScript arm,
  which previously reported `:unsupported :cljs` and now runs).
- **`warm-db` warms secondary indices too, opt-in.** A new optional protocol
  `datahike.index.secondary/ISecondaryWarmable` (separate from
  `IVersionedSecondaryIndex`, so existing implementers are untouched) is
  implemented by the stratum, proximum and scriptum adapters, each delegating
  to its library's own warm. `warm-db`'s `:secondary` option — `:none`
  (default) | `:defaults` | `{index-ident opts}` — runs them and attaches
  `:secondary {index-ident envelope}` to the report. Budgets are per index
  family in that family's own units (stratum: tree nodes; scriptum: Lucene
  segment files; proximum: tree nodes over what its eager restore already
  loaded); the shared part is the report envelope, at least
  `{:fetched :ms :budget-exhausted?}`. Off by default because a secondary's
  full warm can dwarf the primary one — turn it on where you have measured it.
- persistent-sorted-set `0.5.141` → `0.5.142`; stratum `0.3.81` → `0.3.82`,
  proximum `0.1.35` → `0.1.36`, scriptum `0.1.29` → `0.1.30` in the test
  alias (the releases carrying each library's warm).

### Breaking changes

- **The local writer now defaults to `:writer-ownership :shared`** — correctness no longer depends on knowing that a second process, container or Lambda execution environment has started writing the same branch. The default re-reads the branch head once per batch and conditionally publishes it wherever the store supports fencing; set `:writer-ownership :exclusive` only when one process owns the writer and the saved head GET matters. For sequential callers this adds one branch-head read per transaction, and `@conn` reads through to storage rather than trusting the in-memory head. Existing databases need no migration: ownership is a connect-time choice, not stored metadata. The experimental self-writer `:streaming?` option remains a deprecated alias (`false` → `:shared`, `true` → `:exclusive`); streaming itself continues to describe whether a writer delivers completed writes into its connection.
- **The `:self` writer config is now a closed key set** — `{:backend :self …}` accepts only `:backend`, `:writer-ownership`, `:transaction-queue-size`, `:commit-queue-size`, `:commit-wait-time`, `:write-fn-map`, `:max-batch`, `:head-conflict-retries`, `:head-conflict-backoff-ms` and `:require-fencing`; anything else raises `:unknown-self-writer-config-keys` at `connect` instead of being silently ignored, and ownership must be `:shared` or `:exclusive`. This is deliberate rather than tidy: a typo must not silently ignore a caller's ownership choice, especially when `:exclusive` opts into a single-process assumption whose failure is silent data loss. If you carry an extra key in `:writer` today, remove it. ([#959])
- **`d/transact` now throws a JVM `Error` instead of returning it** — a fatal failure in the writer (an `AssertionError`, an `OutOfMemoryError`) used to reach the caller wrapped in an `ExecutionException`, so `(catch Exception e …)` caught it but `(ex-data e)` was empty for *every* error the writer raised. Unwrapping the wrapper fixes the `ex-data`, and it means an `Error` now arrives as itself: catchable as `Throwable` or `Error`, no longer as `Exception`. That matters because the alternative was worse — for a short window on this branch an `Error` was neither thrown nor wrapped but *returned in the tx-report position*, so a commit that never became durable was reported to the caller as a success. If you catch writer failures, catch `Throwable` (or `Exception` for the ordinary ones and `Error` separately). ([#963])
- **`:head-conflict` is a new outcome of `d/transact`** — when two processes write the same branch concurrently on a store that supports fencing, the losing transaction is retried and, if the retries are exhausted, raises `{:type :datahike/head-conflict}`. Nothing was applied and nothing was partially applied; re-read and transact again. Previously such a transaction silently overwrote the other process's commit, so code that never saw an error may now see one — that error is the data loss becoming visible, not a new failure. Set `:head-conflict-retries` on the writer to tune it. ([#963])
- **A secondary index that exists in storage and cannot be restored now fails the connect** — previously the failure was logged at WARN and the index dropped, which left a db indistinguishable from one whose index had never been built: the next transaction created an empty instance and the commit overwrote the stored pointer with it, losing the index for good and undetectably. Bind `datahike.writing/*on-secondary-restore-failure*` to `:drop` for the old behaviour if you would rather come up degraded (e.g. a backend that is not multi-process safe and that you can rebuild). ([#959])
- **`gc-storage` applies a 15-minute sweep floor unless the connection holds an exclusive local writer** — the collector's knowledge of in-flight commits is per-process (`datahike.gc-guard`), so under `:writer-ownership :shared` (the default) or a remote writer backend a commit in flight in another process has already written its objects, nothing names them yet, and an unfloored sweep deletes them; that process's head then lands on nothing. The floor (`:min-age-ms`) was already the only cross-process protection, but it defaulted to zero. It now defaults to fifteen minutes whenever this process is not known to be the sole writer, and to zero under `:writer {:backend :self :writer-ownership :exclusive}`. Visible effect: under the default configuration, garbage younger than fifteen minutes survives until the next cycle — reclamation is delayed. The default is a bound on one awaited request, not a guarantee: a writer that does not await its transacts, a process suspended mid-commit, or a clock difference between processes larger than the floor (the `:last-write` stamps the sweep compares against are each writer's own) still exposes that commit — size an explicit `:min-age-ms` above your longest window plus your largest skew. Pass `{:min-age-ms 0}` to restore the unfloored sweep when you know this process is alone. ([#985])
- **Registering a secondary index over existing data now requires `:writer {:backend :self :writer-ownership :exclusive}`** — the asynchronous backfill keeps the writer available during the snapshot scan by journaling concurrent changes in memory and replaying them in one serialized install step. That journal cannot be shared across processes, so under the default `:shared` ownership (and under remote writers) the schema transaction that creates the index is refused with `:secondary-index-backfill-unsupported-writer` instead of committing an index that could lose writes. An index over attributes that hold no datoms yet still becomes `:ready` immediately under any writer. Alongside: a `:building` generation is never flushed, branched, or used as an audit/GC root; the scanned snapshot and the unpublished index nodes are leased against offline and online GC until the ready commit lands (`d/gc-storage` raises `:gc/read-lease-active` meanwhile); a reconnect after a crash mid-backfill re-anchors the scan at the current head so nothing committed by the crashed process is missed; and `branch!` from a historical commit forks that commit's stored index, not the connection's newer live one. ([#980])

### Status changes

- **Export/import (`datahike.migrate`) reworked, and marked Experimental** — type-exact across every builtin value type, full history, deterministic output, tiered integrity that fails closed, bounded memory, and the same implementation on the JVM and ClojureScript/Node. `export-db` / `import-db` and the dump format are the settled part; the record seam (`import-source` / `export-to-sink`) is the newest surface and the likeliest to move, since each adapter written against it is a fresh test of whether its shape is right, and so far there is one. **Experimental rather than Beta on purpose**: Beta is a promise about a contract, and the work that built this one also found a short export certifying itself as intact, a failed chunk read becoming an empty one, an `:xform` applied twice, and an `import-db` returning two different types depending on the format it was handed. All are fixed and guarded, and none was visible until someone looked — so it wants field use before the promise. Please try it on real data and report what breaks. `datahike.migrate.datomic` is likewise **Experimental** and deliberately held at arm's length (its own source path, no dependency datahike carries, reachable only if you supply the Datomic peer jar); it may move out into a library of its own, which nothing in datahike depending on it is meant to keep cheap.

- **Query planner promoted to the default engine** — the compiled query planner ([#795]) now runs by default; the relational (base) engine remains a permanent fallback for the query shapes the planner declines (multi-source disjoint joins, nested temporal wrappers, stats). The selector dynamic var was renamed `datahike.query/*force-legacy*` → **`*disable-planner*`** (same polarity), and the opt-*in* env `DATAHIKE_QUERY_PLANNER=true` became an opt-*out* `DATAHIKE_QUERY_PLANNER=false`. CI now runs the full suite under both engines on every build. **Beta — newly the default**, so if a query returns wrong or surprising results please [open an issue](https://github.com/replikativ/datahike/issues); you can fall back any time with `DATAHIKE_QUERY_PLANNER=false` (or `(binding [datahike.query/*disable-planner* true] …)`). ([#844])

### Features

- **Optimistic overlays redesigned and promoted to Beta** — `datahike.optimistic`
  now exposes explicit `open`/`close!` resources with O(1) snapshot reads, one
  serialized transition timeline, exact overlay membership changes, honest
  invalidation for base replacements, tagged one-shot outcomes, and separate
  writer-backed versus externally acknowledged prediction lifecycles. The old
  connection-global `register!` / `unregister!` / `transact-local!` surface and
  TxReport-shaped listener claim are removed. This is intentionally breaking:
  validation is asynchronous, listeners receive snapshot transitions, and
  accepted predictions are retained if synchronization stalls. JavaScript and
  TypeScript bindings are included. Kabel writer waiters are now correlated by
  request UUID rather than `:max-tx`, so multiple calls in one writer batch
  cannot overwrite one another. See [Optimistic overlays](doc/optimistic-overlay.md).
- **Long-running operations protect themselves from GC by default** — `export-db` pins the snapshot it reads for the export's duration; `import-db` roots its restored blobs from first write to last commit; a bulk index build (`:build-indexes? true`) maintains a durable checkpoint that gains each completed index family, so a collector in *any* process spares hours of finished work. All of it rides on durable GC roots ([#987]); root records may now name only some index families and may carry literal store keys under `:datahike.gc/keys` (spared by the sweep and reported by `reachable-store-refs`). Nothing to configure and no API involved — the `datahike.gc-roots` functions remain *Experimental* only as an API surface, for pinning **your own** long-lived snapshots (a reporting job over an old `(d/db conn)`). Declaring a root is best-effort (a store that cannot take one warns and falls back to the guard and the floor); a lease lost mid-operation fails it with `:gc/root-lost` instead of publishing what may be gone. The build checkpoint is JVM-only for now. See the new *GC safety contract* section in `doc/gc.md`. ([#990])
- **Durable GC roots (`datahike.gc-roots`)** *(Experimental)* — a process can persist a root in the store: a commit-shaped record the collector's mark walks in addition to the branch heads, so a `gc-storage` in *any* process keeps what it names. Three kinds: `:pin` (one commit, for a long reader of an old snapshot), `:checkpoint` (a synthetic record naming a build's partial trees, for a long builder), `:ref` (a commit and its ancestry under the usual `remove-before` gating). Roots carry a lease — `pin!`/`root!`, `renew!`, `release!`, `start-renewal!` — and a collector reaps an entry once it is past expiry by its own TTL; a holder whose entry is gone gets `:gc/root-lost` (also from the publish-time check `assert-live!`) and must not publish on top of it. `reachable-store-refs` includes blobs named only by a rooted commit; online GC pauses while any root exists, since a rooted record older than the head makes freed-address hints unsound. With no roots declared the registry is never written and the mark is unchanged. This is the mechanism the secondary-index backfill and bulk import will move onto; it does not yet replace their in-process guards. ([#987])
- **`:build-indexes?` takes a computed `:eids` mapping** *(Experimental)* — the bulk index-build path defaults to `:eids :preserve` precisely so it needs no id map, but a Datomic source cannot use that default (its eids exceed `emax` by four orders of magnitude), leaving `:allocate` and its one-entry-per-entity map — ~7.2 GB at 1.1e8 entities before the estimator's 1.6x margin, which is what puts a large migration out of reach of the machine running it. A caller who can COMPUTE the mapping needs none of it, and `ids/apply-mapping` already read ids with `(get eids e e)`, so an `ILookup` was always its contract; what was missing was everything around it — the option schema rejected one at the entry point, the refusal excluded every caller mapping, and `:max-eid`/`:id-map-size` read `:next-eid`/`count` off a map a computed mapping does not have. `:offset` remains the one refused policy here, because it positions a dump above a target's existing ids and this path only ever builds into an empty database. **One mapping vocabulary now, not two**: the streaming path CALLED a function while the bulk path `get`-ed it, and `(get some-fn k nf)` is `nf` — so a function that worked on one silently mapped NOTHING on the other, leaving every id unchanged with no error and a clean report; `ids/lookup-id` is the single owner both paths read through, and a map, a function or an `ILookup` works on either. Two defects surfaced while proving it, both fixed: a **partial** mapping memoised its allocations nowhere, so every datom of an unnamed entity got a separate fresh eid (measured on the previous release — a two-attribute schema at eids `(1 4)` with one attribute's three datoms scattered across them, so it never became a ref and its ref value stayed as the untranslated source id: a dangling reference, silently); and a mapping landing an entity at or above `tx0` imported *successfully* while publishing a `:max-eid` a later transact would allocate straight through, now refused as `:import/eid-above-tx0`. A caller mapping must be **total** — for an id it does not name the streaming path allocates while the bulk path passes it through, since the bulk path has no allocator — and non-injectivity stays the caller's contract, because detecting it needs the O(entities) map the feature exists to avoid. ([#970])
- **Head fencing for shared writers** — the `:self` writer now writes the branch head *conditionally* on stores that can compare-and-set, so two processes transacting the same branch at the same time no longer silently overwrite each other: the loser is rejected and its transaction re-applied against the head that moved. Branch creation, deletion and forced publication also fence the shared `:branches` GC whitelist, and database creation conditionally claims the initial `:db` head, so lifecycle operations cannot erase one another's pointers. Shared ownership already made *alternating* processes safe (#959); this covers overlap. Konserve reports how far a store's guarantee reaches as a domain — `:process` (memory), `:machine` (filestore, OS advisory lock), `:global` (S3, `If-Match`) — and fencing is used automatically where available and skipped where it is not. Because skipping is silent, a deployment that depends on fencing should demand it: `:require-fencing :global` refuses the connect on a store that cannot fence that far, rather than running unfenced. Retries are configurable with `:head-conflict-retries` (default 3), `:head-conflict-backoff-ms` (25) and `:max-batch` (64); only `transact!` and `load-entities` are retried, since re-running a branch merge against a moved head would change what the merge means. See [Concurrent processes](doc/config.md#concurrent-processes-head-fencing). ([#963], [#878])

- **Prepared execution (`datahike.query.execute/*prepared-execution*`, opt-in)** *(Experimental)* — value-free plan reuse for parameterized workloads: with the flag bound true (typically alongside `*fold-scalar-ins*` false), scalar/tuple `:in` bindings are kept out of the plan-cache key and absorbed as per-call constants at execution; single-entity-group point shapes (unique-attribute AVET seek + cardinality-one merges) compile once per plan into a point program that subsequent executions run directly — one cached plan and one compiled program serve every argument value. Default `false`: every path behaves exactly as before (verified by an inertness review and a flag-off differential test). Point paths honor `:cancel`; queries with lookup-ref bindings stay on the relation path. Ships with `datahike.test.prepared-execution-test` — a 14-shape × 4-engine differential (legacy / planner / prepared / prepared+result-cache must agree). ([#936])
- **Index-backfill migration (`:allow-index-backfill?`, opt-in)** *(Experimental)* — enabling `:db/index` (or adding `:db/unique`) on an attribute that already has datoms was rejected, because AVET was never populated for pre-existing datoms. With `:allow-index-backfill? true` in the database config, the end-of-transaction migration sweeps the attribute's datoms into AVET (and the temporal index on history databases); `:db/unique` addition first verifies existing values are distinct (index-equality semantics, so equal-content arrays are duplicates) and rejects on violation, after which uniqueness is enforced against pre-existing values and lookup refs resolve through the backfilled index. Without the flag the historical rejection is unchanged; unused attributes are accepted as before. Disabling `:db/index` remains invalid. ([#934])
- **The distributed wire is CBOR, not fressian** — `datahike.kabel.cbor-handlers` replaces `datahike.kabel.fressian-handlers`, which is **removed**; there is no dual path to configure. Datom, DB and TxReport, plus the persistent-sorted-set nodes and roots, now travel as [RFC 8949](https://www.rfc-editor.org/rfc/rfc8949) CBOR over [boring](https://github.com/replikativ/boring) on kabel frame 14. Two things follow that fressian could not give: the same codec runs in the **browser** from one implementation (fressian's ClojureScript port is a separate library with its own behaviour — it narrows doubles to float32, among other differences), and the frames are an IETF standard that a non-Clojure peer can read with its own CBOR library. **Breaking for anyone who wired the middleware by hand**: swap `datahike-fressian-middleware` for `datahike-cbor-middleware`; see [Distributed](doc/distributed.md). A live deployment that must roll peers one at a time can stage the change through `kabel.middleware.dual`, which reads both formats while still writing the old one. ([#930])

- **Verifiable export/import (`datahike.migrate`)** — `export-db`/`import-db` produce and consume a *type-exact* dump that round-trips full history, every builtin value type (fixing [#633]), schema ordering ([#262]), the tx log ([#377]) and attribute-refs databases ([#508]) without re-inserting system datoms ([#531]). The dump is a **directory**: an EDN `manifest.edn` — human-readable because you read it before you know the codec, and written LAST as the commit marker — plus numbered chunks that are [RFC 8742](https://www.rfc-editor.org/rfc/rfc8742) CBOR sequences under boring's `:archival` profile, so two exports of the same database are byte-identical. **gzip by default** (~6.5x smaller and ~33% faster than uncompressed on a real dump, with no dependency on either runtime); `{:compression :none}` opts out. A target may be a filesystem path **or a konserve store** (S3 / S3-compatible / JDBC / in-memory / IndexedDB), so a diskless container backs up straight to its configured store, and a browser — which has no directories — has a medium at all. Memory is bounded throughout: `:chunk-size` datoms per chunk, `:sort-buffer` datoms per in-memory sort run, and an external merge sort that spills sorted runs rather than holding the database; `{:sort? false}` needs **no scratch space at all** for hard read-only targets, at the cost of not ordering a same-transaction card-one replacement. Integrity is tiered — per-chunk SHA-256 and an order-independent semantic digest validated on open, counts, and an id-independent fingerprint comparing the dump against a live database (`verify`). `:db.type/store-ref` blobs are carried with the dump and verified by content hash. Integrity **fails closed**: a dump whose manifest declares no `:sha256` is refused rather than certified intact, and `:checksums :skip` is the only way past it — explicit, and warned about. `:xform` is a **transducer** over `[e a v t op]` records — `(comp (remove schema-datom?) (map rewrite-value))` — covering attribute renames, value rewrites, unit conversion, redaction and filtering as one streaming operation; one instance spans the whole import, so `(take n)` takes n from the *stream* rather than n per chunk, and net-removed records are subtracted from the expected count so a deliberate drop is not reported as corruption. `{:check-refs? true}` reports ref values naming an entity that holds no datoms. Import refuses a target it cannot accept *before* writing anything (format version, config compatibility, non-empty target) and is **not resumable**: recreate and restart. **Runs on ClojureScript/Node as well as the JVM**, from one implementation under `async+sync` — including the external merge sort. Old single-file CBOR dumps are still read on import (JVM-only). See [Migration](doc/migration.md). *Experimental* — see Status changes above for why not Beta. ([#930])
- **Build a fresh database from a dump (`import-db … {:build-indexes? true}`)** *(Experimental)* — restore by building the index trees directly from sorted input instead of replaying the dump datom by datom. This is the *fresh-database* case, not bulk ingestion in general: it refuses a non-empty target and refuses `:merge?`, because trees built from sorted input cannot apply the upsert semantics `load-entities` applies when datoms meet existing data. The dump is normalised to one file, sorted three times, and all six trees are constructed from sorted streams — the temporal comparator is a refinement of the current one, so one sorted file feeds both trees of a family — then published in **one commit**. The result is a database equal field-for-field to the one the default path produces: all six indexes, `:hash`, `:schema`, `:rschema`, `:max-eid` and the ident maps, verified against the streaming import over a generator built from the shapes that make history non-obvious (card-one overwrite, retract-then-reassert, `:db/noHistory` overwrite, fully retracted entity). One difference, by design: `:op-count` differs, which is inert for persistent-set. (`:max-tx` used to differ too — the streaming path landed one higher — but that was a bug in the streaming path, now fixed, and the two agree.) **`:eids` defaults to `:preserve` here**, unlike the streaming path — an empty target has nothing for a source id to collide with, so the dump's ids are kept, which removes the O(entities) id map (the term `estimate-import-memory` calls the dominant one), removes one of the two reads of the dump, and makes a `:history? true` restore *id-identical* to its source. Opt-in and narrow — **refused, with the reason, rather than silently downgraded** for a merge, a non-empty target, a non-persistent-set index, `:attribute-refs? true`, a dump declaring a secondary index, an `:eids` policy other than `:preserve`/`:allocate`, a manifest with no schema. Runs on **ClojureScript/Node** as well as the JVM: the two refusals that used to name a runtime (`:sync? false` and ClojureScript) described an implementation rather than anything the builder cannot reproduce, and are gone — the dump read and the tree build are awaited, while the three sorts in between read a local scratch spool with synchronous primitives on both runtimes. **No speedup figure is quoted**: the earlier one was withdrawn as unsound and has not been re-measured end to end.
- **Import from and export to anything (`import-source` / `export-to-sink`)** *(Experimental)* — the dump format was previously the only way in or out, so "datahike migrates from anywhere" was half true at best: a caller could neither hand datahike records it produced itself nor receive datahike's records without a dump on a disk or in a store between them. Both directions are now public, over one record shape — `[e a v t op]`, the same tuples the dump holds. A **source** is `{:chunks [descriptor …] :read (fn [descriptor opts] …)}`: descriptors are opaque to datahike, `:read` may park and therefore may do real IO (an HTTP fetch, a Datomic log read, a file read), and everything `import-db` accepts — `:batch-size` `:xform` `:eids` `:merge?` `:build-indexes?` `:on-error` — applies unchanged. What a dump alone provides is passed as `:source-meta` `{:history? :expected-count :max-tx}`, all three optional: a source that cannot count itself simply gets no count check rather than being refused or silently certified. `records->chunk-src` wraps an in-memory sequence for the simple case. A **sink** is `{:open :write :close}`, each awaited, and receives exactly the records `export-db` would have written, in the same order, through the same `:xform` — one function builds the stream for both paths, so they cannot drift about its order, its transducer, or which builder `:sort?` selects. Chunks handed to a sink are **transaction-aligned**: `:chunk-size` is a minimum that grows to the next change of `t`, because a sink that transacts what it is handed would otherwise commit a fragment of a transaction on its own. (`export-db`'s own chunking does not do this and does not need to — a dump chunk is a byte range whose reader reassembles the stream.) The two compose with nothing in between: out through a sink and back in through a source reproduces the database, history and refs included. Both run on **ClojureScript/Node** as well as the JVM, which is where the async contract actually bites — `default-sync?` is false there, so a `:read` returning a plain collection rather than a channel is the *default* failure, not an exotic one. Three combinations are refused rather than silently downgraded: `export-to-sink` with `{:sort? false}` (that mode walks `:eavt`, so `t` interleaves and a transaction lands in many chunks — measured, `:chunk-size 40`: sorted split nothing across 9 chunks, unsorted put two transactions in all nine), and `{:build-indexes? true}` with `{:on-error :collect}` (the index-build path neither validates records nor collects faults, so a malformed record was written into the index and reported as zero errors — measured, `[:OK 11 []]` where the streaming path gave `[:OK 10 [{:error :import/malformed-record …}]]`).
- **A restore no longer depends on `:batch-size`** — importing a dump produced datoms whose `tx` component varied with the batch size, because `transact-entities-directly` bumped `max-tx` once per `load-entities` **call** on top of the correct bump per source transaction, skipping a transaction id at every batch boundary. Measured on a six-transaction fixture: 240 of 253 datoms differed between `:batch-size 5` and a single batch. Entity ids, attributes, values and `:hash` were never affected (Datom hashing covers only `[e a v]`), but `as-of`, `since`, `tx-range` and `diff` all read `tx`, so two restores of one dump could not be compared. The per-call bump is gone: **a restore is now `max-tx`-identical to its source**, `:max-tx-drift` is 0 for a faithful restore rather than +1, and the streaming and index-build paths agree. `max-tx` also no longer points at a transaction id that no datom uses. **Behaviour change**: re-importing an existing dump yields different (more faithful) `tx` values than before, so anything that recorded transaction ids from an earlier restore will see them shift once. Relatedly, the import batcher gained a ceiling — `4 ×` `:batch-size`, overridable with `:max-pending` — because it previously flushed *only* at a transaction boundary, so a dump whose datoms all share one transaction (any database built by a single large `transact`, or by `load-entities`) never flushed and buffered entirely in memory, defeating the `:chunk-size`/`:batch-size` bound on exactly the databases large enough to need it.
- **What changed between two database values (`datahike.experimental.diff`)** *(Experimental)* — `diff` returns `{:added [...] :removed [...]}` for two db values, and `tx-range` returns `[{:t <tx> :data [datom ...]} ...]` for the transactions between them. The cost is proportional to the CHANGE, not to the database: datahike's indexes are persistent trees, so two versions share every node they have in common and a subtree present in both cannot contain a difference — measured at 6 / 6 / 10 index nodes read for a one-datom delta over databases of 2k / 20k / 100k datoms (16 / 157 / 785 nodes), against a cold store. That makes catching a replica or a migration target up practical without holding a `d/listen!` open on the production machine and buffering the backlog there. `tx-range`'s reconstruction is verified equal to the `:tx-data` the transactor itself reported, over a window containing a card-one overwrite, a card-many retraction, a `retractEntity`, and an assert-then-retract inside a single transaction. It requires `:keep-history? true` — without history a retraction leaves no record of the transaction that made it — and it refuses a view from `as-of`/`since`/`history`/`filter`, which wrap an origin db and hold no indexes of their own, rather than reporting no changes. Persistent-set indexes only. **The older version's nodes must still be in the store**: `d/gc-storage` reclaims exactly the nodes the newer database no longer references, which are the ones a diff must read, and a diff across a GC boundary raises `:diff/garbage-collected` rather than a missing-node error. Deliberately outside `datahike.api` while the return shape settles. Runs on **ClojureScript/Node** as well as the JVM.
- **A shared `:self` writer for alternating processes (`:writer {:backend :self :writer-ownership :shared}`)** — the shared writer re-reads the branch head before every batch and applies it to whatever is actually stored, secondary indices included (the head is identified by its commit-id, so an *unmoved* head costs one konserve read and rebuilds nothing). This is now the default; `:writer-ownership :exclusive` preserves the old single-process fast path. `@conn` follows the same rule. **Commit batching survives**: transactions already queued when one commits are chained onto it and share its head read, so a burst of concurrent callers costs a handful of reads rather than one each (measured: 500 concurrent transacts → 9 head reads) — the chain is bounded and never *waits* for more work, so it costs no latency. Relatedly, a secondary index that exists in storage and fails to restore now **aborts the connect** instead of being dropped: continuing produced a db indistinguishable from one whose index had never been built, so the next transaction overwrote the stored pointer with an empty index and lost it for good (bind `datahike.writing/*on-secondary-restore-failure*` to `:drop` for the old behaviour). Scriptum (Lucene) remains single-process. Ownership is a property of the connecting process, not of the stored database, so an existing database can switch modes without migration. *Experimental.* ([#959])
- **cljs async foundation — the storage seam speaks async, per-read** — groundwork for browser clients querying remote backends (IndexedDB, S3). The index storage layer (`CachedStorage.restore`) now honors `{:sync? false}`: a datahike-LRU hit resolves on the calling stack (partial-cps trampolining — all-warm async computations complete *synchronously*, the property the upcoming async engine's sync mode rests on); an LRU miss tries the synchronous store read first — sync-capability is a property of **each read**, not of the store: a tiered store serves its warm memory frontend synchronously and only a frontend miss needs the async backend, so the browser deployment's synced working set stays on the trampoline — and only reads the store genuinely cannot serve synchronously fall back to the channel-adapted async path, where real IO dominates the hop. The synchronous API surfaces such a read as an actionable error (`:storage/sync-read-unavailable`) instead of konserve's internal assertion. DataScript-style synchronous use over memory / synced tiered stores is unchanged. *Experimental.* ([#886])
- **Content identity for unstructured input (`:identity :content`)** — `datahike.experimental.unstructured` can now share structurally identical nested objects instead of duplicating them. By default every nested map is its own entity; `(transact-unstructured conn data {:identity :content})` gives each nested map a recursive `hasch` content id under a `:db.unique/identity` attribute, so identical value objects collapse to one shared entity — recursively (a shared grand-child is one entity though its parents differ) and immutably (change the content and the id changes, so you can never alias-and-mutate a value object). This is content-addressing one level up from index nodes and blobs: sharing appears in the datom graph as it does in the store. Content identity gives *value* semantics and merges coincidentally-identical maps, so for *record* semantics you still declare a natural `:db.unique/identity` key, which datahike's ordinary upsert dedups under either mode. Default behaviour is unchanged. See [Unstructured input](doc/unstructured.md). *Experimental.* ([#882])
- **Blobs and out-of-line values (`:db.type/store-ref`)** — a datom value can now **name an object** — a PDF, an image, model weights — and the garbage collector will **mark** it. The rule is *the database is the root set*: an object lives iff a datom names it; retract the datom and it becomes collectable; keep history and it stays live, because an `as-of` read can still reach the datom naming it. **Where the bytes live is your choice, and the same type covers both**: put them in the database's own konserve store (`k/bassoc` under a `hasch` content hash) and `d/gc-storage` reclaims them for you, portably, on every backend — or `PUT` them straight to a raw S3 prefix from the browser with a presigned URL and a content-type, so they never transit your JVM, and use the new **`datahike.gc/reachable-store-refs`** to get the live set and sweep your own prefix. Datahike owns the hard half (what is still referenced, across branches and through retained history, honouring `remove-before`); you own the listing and deleting. Schema shapes that would defeat the mark are **rejected** rather than documented: a store-ref inside a `:db/tupleType` (the tuple's own valueType is `:db.type/tuple`, so the nested keys are invisible to the mark) and `:db/noHistory` + store-ref (retracted values are not retained, so history could name a collected object) — checked on the *resulting* schema at the datom level, so adding `:db/noHistory` to a live store-ref in a **later** transaction (a partial entity map or a raw `[:db/add …]`) is rejected too, not only the all-in-one declaration. **Not for structured data** — if you would ever filter or join on something *inside* the value, it is a document: transact it as datoms or index it. **In-store blobs also replicate causally**: the konserve-sync walker moved into datahike (`datahike.kabel.walker`) and now follows store-ref values via the new **`datahike.gc/record-store-refs`**, so a blob is shipped to a subscriber *with* the datoms that name it — ahead of the branch head — rather than leaving a live reference to an object that never arrived (the same blind spot the GC mark had). See [Blobs and out-of-line values](doc/store-refs.md). *Experimental.* ([#881])
- **diff-buf write-buffering (per-store, opt-in)** — persistent-sorted-set's diff-buf buffers a commit's content-only child diffs inside the rewritten ancestor instead of rewriting the whole root→leaf spine, cutting small-commit object writes from ~`depth+1` PUTs per index to ~1 — the biggest win on request-priced object stores. Enable at database creation with `:index-config {:diff-buf-size 256}` (default `0` = off; the on-disk format is unchanged when off). The setting is create-time-fixed and adopted from the store at connect, so reconnects don't need to re-specify it (an explicitly conflicting value raises). Composes with `:crypto-hash?`: a branch's content address folds its buffered diffs, so the merkle audit (`datahike.audit/verify-chain :deep?`) detects slot tampering like any other content; note the hash is representation-dependent — identical logical content hashes differently under different `:diff-buf-size` settings. On-disk format requires persistent-sorted-set ≥ 0.4.126 (older readers refuse slot-bearing stores via the existing version guard); **correctness requires ≥ 0.5.140**, which is what this pins. 0.4.136 made a commit's settle atomically published against a pipelining writer's structural-sharing copies (NodeState) and 0.4.137 made diff-buf projection land on a copy, but 0.5.140 is the floor: it carries a correctness pass over diff-buf and the B-tree, including a stale separator that could leave a datom present but unreachable by a fully-specified lookup (see persistent-sorted-set's `doc/advisory-stale-separator.md` — it affects 0.3.114 through 0.4.139, and repair is export + re-import). See [Reducing write amplification](doc/write-amplification.md). *Experimental.* ([#867])
- **Index-root fusion (opt-in)** — `:fuse-index-roots? true` inlines each index's root node into the db-record so `commit!` skips writing those roots as separate objects: one fewer PUT per index per commit and one fewer GET per index on cold open; a single-leaf index (tiny tenant) collapses to ~1 object write per commit. Composes with diff-buf. Restore is presence-based (fused and legacy records both reconnect; the stored flag is adopted at connect), GC and the merkle audit walk seeded inlined roots, and under `:crypto-hash?` the roots stay separate objects (content-address dedup could alias a root as another tree's child) so fusion there saves the cold-open GETs only. See [Reducing write amplification](doc/write-amplification.md). *Experimental.* ([#867])
- **Commit graph opt-out (`:commit-graph? false`)** — every commit normally persists an immutable record under its commit-id, forming the provenance chain consumed by `datahike.audit/verify-chain`, ancestry walks, `branch!`-from-commit-id, and `dh://…?commit=` references. Stores that need none of these (typical `:keep-history? false` tenants) can now opt out at creation: commits then write only the branch head — the dominant per-commit garbage object disappears (measured ~87% of garbage objects under sustained load) and, combined with `:fuse-index-roots?` and diff-buf, a buffered commit becomes a **single object write**, which also makes S3-conditional-write fencing possible. The commit-id is still computed and stamped in `:meta` (identity, sync dedup, and the writer's head-cid threading are unaffected), one-step lineage is still recorded, and time travel (`as-of`/`history`) is unaffected — history lives in the temporal indices, not the commit graph. The flag is store-fixed and adopted at connect like `:fuse-index-roots?`; combining it with `:crypto-hash? true` is rejected at creation, and `branch!` from a commit-id fails with a self-explaining error (branching from a branch works unchanged). See [Reducing write amplification](doc/write-amplification.md). *Experimental.* ([#869])
- **Background concurrent GC (`datahike.gc/start-background-gc!`)** — periodic full-reachability mark-and-sweep that runs *concurrently* with an active writer: marking is read-only, and the sweep stops at the store's **safe point** rather than at `now`, so the objects of a commit that is mid-flush — written, but not yet named by any head — are spared. This requires the writers and the collector to be **in the same process** (see [#879]). Unlike the freed-address online GC it supports **multiple branches**, needs no mutation-time tracking (it reclaims garbage that freed-tracking cannot see, e.g. under a pipelining writer), and prunes commit-graph history when `:history-window-ms` is set (retention is governed entirely by that / `gc-storage!`'s `remove-before`). The two collectors compose: prefer online GC's freed-tracking + freelist recycling for single-branch bulk imports (O(garbage), keeps object counts flat), and this collector as the completeness pass. Cross-platform (JVM + cljs). *Experimental.* ([#868], [#879])
- **Cross-database references (`datahike.reference`)** — value-level references that point *across* stores in a distributed deployment, serialized as `dh://` URIs. A reference is the triple **(db-id, selector, temporal)**: store `:id` + a `[unique-attr value]` lookup ref or bare entity id + an optional version. The URI temporal is a standard URL query string — `dh://<db-id>/<attr>/<value>?tx=…&date=…&valid=…&commit=<uuid>&branch=…` — where `?commit=<uuid>` pins an exact content-addressed commit (resolved via `commit-as-db`), the most precise record reference. `render`/`parse` round-trip and encode a selector value of **any** datahike value type — readable tags for the identity-friendly scalars (untagged UUID, `str:`/`long:`/`kw:`/`bool:`/`inst:`), `flt:`/`b64:` for float/bytes, and an `edn:` fallback that losslessly preserves `bigint`, `bigdec` (with scale), `double`, `symbol`, and `tuple`. `resolve-reference` is strict-by-default (selector must be `:db/unique`) with explicit opt-in for non-unique selectors, and takes an injected `connect-fn` so deployments own peer/grant/branch selection. Outgoing links can be reified as datalog-queryable `:dh.ref/*` entities. *Experimental.* ([#852])
- **Attribute-value constraints** — opt-in per-attribute value validation. `:db/maxLength` bounds a value's length — chars for a `:db.type/string`, bytes for a `:db.type/bytes` — declarative and cljs-safe; `:db.attr/preds` names value predicates by symbol (like `:db.entity/preds`), each resolved via a process-local registry (`datahike.attr-preds/register-attr-pred!` — the cross-platform path) or, on clj, a `requiring-resolve`-able var (Datomic-style). Predicates are `(fn [value] -> truthy)`; a non-`true` return aborts the transaction with `:transact/attr-pred`. Enforced on assertion only (never on retract) under **both** `:read` and `:write` schema-flexibility, gated on an O(1) rschema lookup so unconstrained attributes pay nothing, and addable to already-defined attributes. Under `:attribute-refs? true` the constraint attrs get stable system entity IDs (like `:db.secondary/*`); a pre-existing attribute-refs store needs an ident-ref-map migration before it can use them. *Experimental.* ([#861])
- **Opt-in value-size caps** — value-size caps bound oversized values that would otherwise silently bloat the index and hit backend limits (e.g. a 32 KB string re-writes ~30 MB per neighbouring commit; DynamoDB items cap at 400 KB). They are **opt-in**: pass `:value-caps :default` at `create-database` for the Datomic-parity caps (`:db.type/string` → 4096 chars, `:db.type/bytes` → 4096 bytes, string slots inside a `:db.type/tuple` → 256 chars), or set `:max-string-length` / `:max-bytes-length` / `:max-tuple-string-length` individually (`0` disables one; an explicit key wins over the preset). A per-attribute `:db/maxLength` always wins and applies under both `:read` and `:write`; the config-level caps apply only under `:write` and to user attributes (`:db/doc` and other system string attrs, and `:db.secondary/only` values, are exempt), and raise `:transact/max-length`. **A database created without any of these is left unbounded** (unchanged from before the feature), and `create-database` logs a one-time warning nudging you to make the choice explicit. Store large payloads off-database as a pointer or in a secondary index. *Experimental.* ([#861])
- **Store-level transaction predicates** (`datahike.tx-preds`) — the `tx`-level member of the predicate family, complementing `:db.attr/preds` (per value, on assertion) and `:db.entity/preds` (per entity, opt-in via `:db/ensure`). A tx-pred is `(fn [tx-report] -> …)` registered per store-id (`datahike.tx-preds/register-tx-pred!`, out of band — never placed in the serialized config) and run on the fully-resolved report (`{:db-before :db-after :tx-data}`, real eids + retract flags) of **every** committed write; a thrown `Exception` (not an `Error`) rejects the transaction — the error reaches the caller, the chain does not advance, nothing persists. Unlike `:db/ensure` it is **mandatory** (fires regardless of the transaction's shape — the trust-boundary property a governed store needs) and, because it sees the resolved retract flags, it can also guard **destructive** operations. Ungoverned stores pay a single map lookup. *Experimental / internal.* ([#861])
- **`:db.secondary/only` — out-of-line values** — flag a string attribute `:db.secondary/only true` to store its value *only* in the covering secondary index (Scriptum/Lucene); the primary EAVT/AEVT/AVET hold a `hasch` content hash in its place, keeping the primary indices small for large/unbounded payloads (transcripts, web pages, agent context) while the value stays fully searchable. Retraction/uniqueness/dedup work on the hash. The whole `:db.secondary/*` schema family was graduated into the system schema (stable entity IDs, mirroring `:db.valid/*`) so secondary indices align across attribute-refs databases. **Search-only** — the value is not reproducible from the primary; declare it only where the canonical value lives elsewhere. *Experimental.* ([#840])

- **Datomic Pro → datahike migration (`datahike.migrate.datomic`)** *(Experimental)* — a source and a sink for the migrate record seam, so a Datomic database exports to a datahike dump and a datahike database imports into Datomic, both streaming through the same `[e a v t op]` records as every other adapter. Held at arm's length on purpose: it lives on its own source path (`src-datomic`), datahike takes **no dependency** on the Datomic peer jar, and the namespace is reachable only if you supply one — so it may move out into a library of its own without anything in datahike having to change. Full history transfers as history, and transaction times and ordering are preserved — but entity and transaction **ids are remapped in both directions**, so a round trip is value- and history-identical rather than id-identical. That is a hard limit, not a shortcut: a Datomic user eid is around 1.76e13 against datahike's `emax` of 2 147 483 647, four orders of magnitude above the ceiling, and datahike does not range-check an incoming eid — it silently reallocates. So `{:eids :preserve}` is REFUSED against a Datomic source rather than quietly downgraded. Scope is stated in the namespace docstring rather than implied: Datomic **Pro** via the peer API only (Cloud and Local speak the client API, which has no `d/log` and so no readable history), and `:db.type/uri` values are carried as strings because datahike has no such type. See [Migration](doc/migration.md). ([#930])

- **`:db.secondary/only` names which value a datom means, or refuses** — the primary indexes hold only a content hash for such an attribute, so the secondary index IS the storage, and `export-db` reads values back out of it through `ISecondaryScannable`. That read was keyed on `[attr eid]`, which does not identify a value, and two shapes failed **silently, producing a backup that restores to different data**: a `:db.cardinality/many` attribute exported one value repeated once per datom (measured: tags `"alpha"` and `"beta"` on one entity gave a dump holding `"alpha"` twice and no `"beta"`), and a `{:history? true}` export of an overwritten value wrote *today's* value onto the historical assertion (`"version-one"` appeared nowhere, and the retraction beside it named a hash the dump never asserts). Export now **checks**: the content hash each datom names is the primary's own value, so whatever the index returns is verified against it, and a value that cannot be confirmed is refused (`:export/secondary-only-unresolvable`, with `:reason` separating "this index answers per entity" from "this index no longer holds that value") rather than guessed. An index that stores values per datom can serve both shapes by implementing the new **`ISecondaryHashAddressable`** (`-sec-value-by-hash`); none of the shipped ones does yet — Stratum is columnar with one cell per `[eid column]` and Proximum is keyed by external id, so for those a second value overwrites the first at *write* time, which is also why a `:db.secondary/only` attribute may now be `:db.cardinality/many` only where a covering index declares that protocol (`:transact/secondary-only-multival-unstorable` at the first such write, instead of silently keeping one value). Current-state export of a cardinality-one attribute — the common case — is unchanged apart from one hash per such datom. ([#930])

- **A retraction removes one datom from a secondary index, not the whole entity** — Scriptum deleted by `_entity_id` alone and Proximum by external id, so retracting ONE datom dropped every value the entity had in that index. Measured: an entity with `:doc/body` and `:doc/title`, both covered by one Scriptum index; retracting `:doc/body` left `:doc/title` unreadable from the index while the primary still held it. For an ordinary attribute that is index drift, repairable by a rebuild — for a `:db.secondary/only` attribute the index is the only copy, so it was **permanent loss of a value the database still reported as present** (and, before export learned to verify content hashes, a backup that silently wrote the hash in its place). Scriptum now deletes by a composite `"<eid>|<attr>"` term — composite because `delete-docs` takes a single Lucene Term, so a conjunction is not expressible without changing its API. One case stays imprecise and is documented at the call site: an ordinary `:db.cardinality/many` attribute still loses that attribute's other values for the entity, because keying on the value would mean hashing it into a term on every add. Proximum needed no change here (it holds one vector per entity, so delete-by-id is exact) but **now refuses an index declaring more than one attribute**: it is keyed by entity id, so two attributes collided under one key — throwing `"External id already exists"` from inside the async index update where an entity had both, and silently answering for the wrong attribute where entities were disjoint, since `-sec-value` can only fetch by id. Declare one Proximum index per vector attribute. ([#930])

- **The Stratum secondary index applies a transaction's CELLS** — the adapter hand-rolled SCD2 (materialize rows, snapshot the previous open row, rebuild column maps), and its transient could only append a whole row or drop a whole row: `pending-adds` held just the columns THIS transaction wrote and was then treated as a complete row. Four measured consequences. A cardinality-one update left a DUPLICATE row whose sibling columns were `nil` — and `-sec-value` (`:limit 1` over an unordered scan) returned the stale one, so a value read back as 50000 after being set to 60000; the index's own `-columnar-aggregate` threw `ArrayIndexOutOfBoundsException` where it worked on a clean dataset. Retracting one attribute dropped the entity's whole row, taking its other attributes with it — permanent loss for a `:db.secondary/only` attribute, whose value the primary does not hold. In valid-time mode every row was stamped `_valid_from 0` AND `_valid_to 0`, a zero-width window valid at no instant, because the tx entity carrying `:db/txInstant` is not in EAVT yet while its own datoms are being applied. And `-sec-value` filtered neither temporal axis, so it read rows an SCD2-on-both-axes update had already superseded. The ~320 lines of hand-rolled SCD2 are gone: both modes now go through Stratum's `upsert!`/`retract!` keyed on `:eid` (one pass for the whole batch, [stratum#36]), `pending-retracts` names `[entity attribute]` rather than the entity, and reads filter both axes. Requires Stratum 0.3.79 ([stratum#37] fixed reading and writing a dict-encoded string column, which no caller had exercised). ([#930])

### Notable fixes (distributed)

- **`import-db` holds the GC guard from the first restored blob to the last commit** — a dump's carried `:db.type/store-ref` blobs are written under their content ids *before* any datom names them, and the datom that finally does may sit in the import's last batch. For the whole import each blob was therefore an object reachable from nothing, and a concurrent `gc-storage` in the same process could delete it while the import went on to report `:verified? true` (verification is count-based). The bulk index build guarded its trees and every commit guarded itself; nothing guarded the blobs. Both media are covered. The guard is per-process, like every guard: an import driven from a process other than the collector's (a remote writer) is covered by the sweep floor, not by this. ([#983])
- **A secondary-index backfill pins its snapshot with a durable GC root** — the scan's base commit is declared as a `:pin` root (see *Durable GC roots*), renewed in the background and released by the ready commit, so a `gc-storage` from any process collects around it. `d/gc-storage` no longer raises `:gc/read-lease-active` for the duration of a backfill (the process-local read lease from [#980] is gone); a build whose lease is lost is discarded at install with `:gc/root-lost` rather than published over swept nodes. ([#989])
- **An unknown writer operation names itself instead of blaming the connection.** `write-fn-map` is a plain map, so an operation it does not hold resolved to `nil` and `(apply nil …)` threw a `NullPointerException` — which the error handler then rewrote as *"connection may have been invalidated, e.g. through db deletion, and needs to be released everywhere"*. A caller whose only fault was naming an operation the writer does not have was sent to inspect their storage. That is the version-skew case (a newer client against an older remote writer, which this wire has no version exchange to catch earlier), and it applied to every operation ever added, not just the new `load-entities-migrating`. The lookup now fails with a typed `:writer/unknown-op` naming the missing operation and listing those the writer does support, and the writer survives it — an unknown op is a caller error, not a fatal one. The NPE hint is kept for errors thrown *inside* an operation, but as a hint with the original exception attached as its cause, rather than a rewrite over a guess.

- **A tx-report broadcast no longer carries an import's id map.** `:migration` is the source-id → target-id mapping an import threads from batch to batch on the tx-report — it has to travel, because the writer owns the database and the caller cannot reach into its loop. The *return* to the calling peer needs it; a *subscriber* does not, and nothing reads it off a broadcast. It was being fanned out anyway: measured at 119 KB of wire for 20 000 entities, and it accumulates across batches, so a million-entity restore would push tens of MB at every subscriber for data none of them looks at. Stripped at the publish site only. Importing through a remote writer is now covered by an integration test (`import-db` through a `KabelWriter`, several batches, asserting a ref resolves — which is only true if the mapping survived the round trip); `doc/migration.md` now says plainly that a large import belongs on the writer's machine, and why.

### Breaking

- **`datahike.migrate/import-db` returns one shape for both dump formats.** It returned the report map for a manifest-and-chunks dump and a `datahike.db.TxReport` for a legacy single-file one — two types from one function, while the docstring promised the map unconditionally. A legacy import now returns the same map. Legacy dumps carry no count to verify against, and their records are not one-for-one with the datoms a correct import leaves (the import stamps its own `:db/txInstant`), so `:verified?` is `nil` and `:verification` is `{:status :unavailable :reason :legacy-format}` — not checked, rather than a check manufactured from the import's own behaviour. Use `verify` to inspect such a dump. The docstring now lists every key returned; seven were previously undocumented.

### Deprecations

- **`datahike.migrate/update-max-tx` moved to `datahike.migrate.legacy` and is deprecated** — the reader for the single-file dump format released datahike wrote now lives in its own namespace, and this helper went with it. `max-tx` is maintained by `load-entities`; the helper only exists for dumps written before that was true, and calling it directly was never documented. **`datahike.migrate/*import-batch-size*` is unaffected and keeps its published home** ([#845]): `import-db` still detects a legacy single-file dump and honours the binding, so existing code needs no change. The new manifest-and-chunks format takes `:batch-size` as an option instead.

### Notable fixes

- **A secondary index that has not been backfilled is no longer queried** — a schema-declared secondary index is created with status `:building` and backfilled by the writer, so a database built with `d/db-with` (no connection, hence no writer) stays `:building` indefinitely and holds only the datoms of transactions made *after* the index was declared. The aggregate path never checked the status, so it answered from that partial index: `(min ?x)` returned `nil` on the declaring transaction and, after a further transaction, the minimum of just the later datoms — a silent wrong answer rather than a stale one. An index whose status is `:building` or `:disabled` is now skipped, matching the check the transaction path already makes; the query falls back to a path that reads the primary indices and is correct. A hand-assembled index (no status) is complete by construction and a `:ready` one has been backfilled, so both keep using the fast path. ([#914])
- **An import naming an attribute the target has not installed says so, instead of a NullPointerException** — with `:attribute-refs? true` a datom's attribute is the attribute's ENTITY ID, and `-ref-for` answers `nil` for an ident that was never installed. That `nil` became the datom's attribute and survived the write, failing much later and much further away inside the index comparator as a bare `NullPointerException: Cannot read field "value" because "anotherLong" is null` — naming neither the attribute nor the record that carried it. It now raises `:transact/unknown-attribute` naming the attribute, enforcing a rule `import-source` already states (a source emits an attribute's schema datoms before the data using it) in the same place and the same way as the configuration-mismatch refusal beside it. Databases without `:attribute-refs?` are unaffected and unchanged: there the attribute IS the keyword, so there is no entity to resolve and an undeclared attribute is simply stored. Reachable from a real Datomic source rather than hypothetical — `migrate.datomic` resolves idents against the CURRENT database, so every historical datom of a renamed attribute already carries the final ident while the `:db/ident` records still replay the rename, and the data therefore arrives before the name it is labelled with exists. That labelling question is [#967], and this fix does not answer it: a Datomic import into an `:attribute-refs?` target still cannot complete, it now fails legibly. ([#968])

- **A Datomic import no longer dies on an attribute rename, and renaming one is now a decision rather than an accident** — `datahike.migrate.datomic/tx->records` sorted a transaction's records by `(txInstant-first, e, a)` with **`op` absent**, while `migrate.sort/sort-key` — the order that sort's own comment claims to implement — carries `op` and documents retraction-before-assertion as "the whole guarantee". For an ident RENAME the retraction and the assertion of `:db/ident` share `(e, a)` exactly, so `sort-by`'s stability handed their order to whatever `d/tx-range` returned, and Datomic returns them **assertion-first**. That reached `update-schema` with a second `:db/ident` for an entity that still held its first, where the `:db/ident` branch merged into `(schema e)` — which by then holds a POINTER to the ident's entry rather than the entry — and `conj` on a keyword threw `ClassCastException`. Reported from a 393-million-datom production import that ran six healthy hours at a steady 10,600 datoms/s and died at 55%, on a single user attribute renamed years earlier; the two bootstrap renames every Datomic database carries pass through harmlessly, which is why it surfaces deep into a run rather than at the start. Three things now agree where only one did: the sort key carries `op`, the record contract reads `(t, txInstant-first, e, a, op)` in all six places it is written down — it had omitted `op` in every one, so a source written against the documented contract inherited the bug — and the `:db/ident` branch follows the pointer exactly as its sibling branch and `remove-schema` already did, making the function total on its own input instead of dependent on an ordering no caller controls. Separately, and independent of any import: renaming an attribute through `d/transact` used to throw that same `ClassCastException` for `[:db/add attr :db/ident :new]`, be refused as `"Update not supported"` as an entity map, and be refused as `"requires the attribute to be unused"` as an explicit retract-then-add — three spellings, three different answers, none of them a rename. What a rename MEANS depends on how a datom stores its attribute, so that is now what decides it: without `:attribute-refs?` the attribute **keyword is the storage key in every datom**, so renaming the ident renames nothing — the old datoms keep answering to the old keyword while the new name starts empty, and the attribute is silently SPLIT across both — and it is refused while the old name still has data, with a message that says so (an unused attribute still renames freely). With `:attribute-refs? true` datoms name the attribute by **entity id**, the existing data answers to the new name the moment the ident changes, and every spelling is allowed. ([#966])

- **Array values are values at the query engine's equality and hashing seams** — a byte, float or double array is a VALUE in datahike (`datahike.array/a=` says so, and the index comparator agrees), but the JVM and JavaScript both give arrays IDENTITY semantics, so every place the engine compared or hashed one silently answered by reference. Measured on `main`, with both engines agreeing wrongly in most cases: `[?e :blob ?v] [?e :blob2 ?v]` over equal-content arrays returned `#{}` on the relational engine (and the two engines DIVERGED — the planner answered correctly); the same join across entity groups returned `#{}` on both; a collection `:in` of an array matched nothing; a `get-else` obligation and a `not-join` both ignored the values entirely. Six seams now share one rule: `val-eq?` (fused merges and point programs) tested JVM byte arrays only, so equal-content **float** and **double** arrays were rejected and ClojureScript compared every array by identity; the obligation against an `:in` constant and the one on a function output used `=`; join keys hashed by identity, and there were **two** key functions — the relational engine hashed through `datahike.query`'s and the planner through `datahike.query.relation`'s, so fixing one left the DEFAULT engine answering `#{}` while the base engine was correct; the planner's hash-probe joins keyed raw values into a `HashSet`/`HashMap` (and on ClojureScript a `js/Set`/`js/Map`, which compares objects by identity whatever their `=`, so the key there must be a primitive — and must not be built with `pr-str`, which honours `*print-length*`); and `not-join`'s exclusion set keyed raw values too, so a negated relation excluded nothing. `wrap-comparable` did not hold the contract its own docstring states (`(a= x y)` iff the wrappings are `=`): byte arrays became a String built with `(char signed-byte)`, which **threw** for every byte from `0x80` up, and float/double arrays plain vectors, whose equality disagrees with `a=` in both directions on NaN and on signed zero. On the JVM a key now snapshots the array and defers to `Arrays/equals` (bit-based for float/double, so it agrees with `Arrays/compare`); the snapshot is not optional, since a key that cached its hash while reading a live array answers `=` to a key whose hash differs and loses entries in every hash collection. This also fixes the uniqueness check in `transact`, which keys array values the same way. **ClojureScript element ORDER is deliberately left as `goog.array/compare3` had it**: `cmp-datoms-avet` breaks a value tie on the entity id, so the old comparator *is* a total order, a stored tree can legitimately hold `[NaN]` before `[1.0]`, and giving elements the JVM's order would silently invalidate trees that have existed since 0.8.1745 with no migration. What that order gets wrong is fixed where it costs nothing on disk — in **equality**: `compare3` finds neither `<` nor `>` between a NaN and a number and so called them EQUAL, making every numeric array equal to every NaN-containing array of the same shape. `a=` now decides array equality element-wise there (a NaN equals only a NaN; `-0.0` is not `0.0`), matching the JVM's value semantics, so the platforms agree on what is equal even though their stored orders differ. Mismatched array KINDS are ranked (byte < double < float, as the JVM's class-name fallback orders them), fixing a real cross-platform disagreement — `(compare-value (byte-array [1]) (float-array [1.0]))` is `-4` on the JVM and was `0` on ClojureScript — with **one narrow migration hazard**: under `:schema-flexibility :read` a single attribute accepts all three kinds at once, and a ClojureScript-built index in exactly that configuration is reordered by the ranking and should be rebuilt. One platform difference is deliberately **not** reconciled: a byte array is unsigned on ClojureScript and signed on the JVM, so `0xff` sorts at opposite ends and the first value a card-many bytes `get-else` returns can differ by platform; changing it would reorder existing stored indexes. The rule reaches the datom layer too: a datom's `=` and `hash` compared its value with Clojure's `=`, so two datoms the INDEX calls one value (`compare-value` returns 0) were two in a set, two under `distinct`, and hashed apart. That leaked out of memory, because a database's `:hash` is a SUM of datom hashes — an array-holding database had a `:hash` **no recomputation could reproduce** (measured: two loads of one stored database recompute to different numbers), and the `:build-indexes?` import path recomputes exactly that way, so a rebuilt array database could not be `:hash`-equal to its source. Datom equality and hashing now use the same value semantics as the index; `wrap-comparable` is identity for every non-array value, so **no array-free database changes its `:hash` by one bit**. `:db.fn/cas` was the same defect on a write path: it compared the expected value with `=`, so a compare-and-swap succeeded only when the caller passed back the very object it had read out of the database — a value reconstructed from the wire, a file or another process failed with nothing wrong. It compares by value now, on both cardinalities. The explicit spelling of an equality now agrees with the implicit one: `[(= ?v ?w)]`, `[(not= ?v ?w)]` and `[(compare ?v ?w)]` went through Clojure's `=`/`compare`, so `[?e :ba ?v] [?e :bau ?v]` selected the entities whose arrays hold the same bytes while `[(= ?v ?w)]` over the same pair answered `#{}` — and `not=` ADMITTED exactly the rows it should have excluded. **Not covered**, at seams this change does not reach: a `:db.type/tuple` value whose components include an array is hashed by identity, so a join over equal-content tuples answers `#{}` while the stored-value comparator gives them content semantics; the result set, `distinct`, grouping and `count-distinct` hash arrays by identity, so two equal-content arrays through a relation input produce two rows, two groups and a `count-distinct` of 2; and an array reaching a RULE head as a folded `:in` constant loses the constraint on the planner — `(has ?e ?v)` over `[[(has ?e ?v) [?e :ba ?v]]]` returns every entity where the relational engine returns the matching two. The first two are identical on both engines and so invisible to differential testing; **the third is a live planner-vs-base divergence**, pre-existing and not introduced here. ([#965])

- **A merge cursor is no longer used over a scan that is not monotonic in entity id** — found alongside the array work and unrelated to it. The fused merge paths walk a forward cursor, which assumes the scan visits entities in increasing `e`; a value-position SIP probe turns the consumer scan into a series of AVET seeks ordered by VALUE, so entities arrive in value order and the cursor cannot seek back. Measured on a two-clause query with no arrays and no `get-else`, over an attribute whose values decrease as `e` increases: the planner returned one row where the relational engine returns two. The gate now sits on the SCAN rather than on the merge, so all three fused paths are covered, and `:sorted-merge` — cursor-driven throughout, with no lookup fallback — routes to `:per-cursor-merge` instead of building a cursor it cannot use. Pre-existing, and silent. ([#965])

- **Binding a variable that is already bound now unifies rather than overwrites** — an occurrence of a bound variable is an equality obligation. Datahike already read it that way for a variable repeated *inside* one clause ([#912], [#913]) and for ordinary data patterns — `[?e :name ?v] [?e :nick ?v]` selects the entities whose nick equals their name — but every clause form that BINDS a value had invented its own rule. `get-else` **overwrote** the binding on the relational engine and **ignored** it on the planner, so `[?e :name ?v] [(get-else $ ?e :nick "zzz") ?v]` answered rows whose two values plainly differ; each slot of a tuple binding overwrote on both engines; and a variable repeated in a rule HEAD (`[(same ?a ?a) …]`) produced `nil`, because both engines substitute head parameters through a map keyed on the parameter list and a repeated key collapses last-wins — which also **silently dropped a ground argument** in that position, so `(same 20 ?y)` answered over every value, and made the relational solver **hang** on a recursive rule. One law, asserted at each of the seven binding sites in one test file that runs on the JVM and on ClojureScript. A related class rides along, found the same way: a value of **`false`** was read as *absent* wherever presence was tested by truthiness — a folded constant of `false` was dropped from the relational engine's obligations, so `[(get-else $ ?e :flag false) ?v]` with `?v` bound to `false` returned the entities whose flag is `true`; a `false` scalar `:in` reached a function or predicate as `nil`, so `[(= ?v ?f)]` matched nothing; and the columnar aggregate dropped a ground `[?e :flag false]` filter, aggregating over exactly the rows it excludes. For an optional merge the correction has three outcomes rather than two: present and satisfying the obligation emits the value, present and failing it **drops the row**, and only genuine absence plants the default — which must then satisfy the obligation itself. Folding the first two into one "not found" is what made the planner assert values the database never held. The same fold was live in the temporal kernel on every view, where the presence probe was additionally asked over a slice already bounded by the obligated value — so it could only ever answer about that one value — and the whole ClojureScript half of that kernel still planted defaults unconditionally while every JVM run was green. The obligation is also judged about the value `get-else` actually returns: it is **single-valued** — the entity's first datom for the attribute, whatever the attribute's cardinality or the temporal view — and seeking at the obligated value instead asked "does SOME datom equal it", which admitted a second card-many value (`:tag [:x :y]` matched an obligation of `:y`) or, on `history`, a later version, and carried the invented row into aggregates. Unification is array-aware, so an obligation between two equal-content byte arrays holds rather than silently dropping the row. One further ClojureScript-only gap surfaced with the temporal tests and is fixed here: the cljs temporal kernel had no `:historical` branch at all, so on Node a `history` query whose merge is card-one — which every `get-else` is — answered from the current index and returned the current value. **Not covered**: a variable repeated inside a single binding form (`[(vector 1 2) [?x ?x]]`) still overwrites on both engines. ([#927])

- **An export no longer holds the whole database in memory on ClojureScript** — `async+sync` compiles one source form to a plain `let` under `{:sync? true}` and to a core.async `go` block otherwise, and `default-sync?` is **false on ClojureScript**, so Node runs the async compilation exclusively. In that compilation a named lazy sequence is retained for the lifetime of the block: core.async only decomposes subforms that *contain* a park, but once a park anywhere in the enclosing form forces decomposition, every `let`/`loop` binding in that region becomes a local inside the state machine's `try` — where Clojure's locals-clearing does not apply — and one read from a second block goes into the state array, which is never nulled. The record stream is the entire database, so an export bounded to `:chunk-size` datoms by design held all of them anyway. Measured on 400k records with used heap sampled inside the block (15 MB baseline): 63 MB retained, against 15 MB with the stream built at the point of use. Note what does *not* help, since both are easy to reintroduce: **moving the park later or earlier changes nothing** (the binding is in the same decomposed region either way), and **the arm that leaks need not be the arm that parks** — a sequence consumed in the non-parking arm of an `if` whose other arm parks is retained identically, which is why the filesystem export path needed the same fix as the store one. Three sites: both arms of `export-db`, `export-to-sink`, and the per-family sort in the index build, which held one family's spool at a time rather than none. The JVM's synchronous default was never affected.
- **Online GC is refused on a diff-buf database rather than corrupting it** — online GC reclaims blobs from persistent-sorted-set's `markFreed` stream, which pss documents as a *hint* and not a reachability claim. Under `:diff-buf-size` that hint is sound only for a **linear** history: a parent's slot names an anchor *plus* a diff, so two versions can name the same anchor and neither owns it, and storing one of them may flush that child — correct for the version being stored, wrong for the other. Measured in pss against a backend that acts on the callback: 25 read failures across 768 trials at budget ≤ 4, while linear histories were clean in 432/432 cells and budget 0 in 864/864. The combination is now refused **at connect**, which is the first point where both values are known (`:diff-buf-size` is create-time-fixed and adopted from the store, `:online-gc` arrives at connect) and which catches the dangerous case: a database created long ago with a budget, later reconnected with online GC switched on. Refused rather than silently disabled, so an operator learns their GC is not running; `:allow-unsafe-config` overrides, after which `online-gc!` skips with a warning instead of acting on the stream. **Offline GC (`d/gc-storage`) is unaffected** and is the supported way to reclaim here — it derives reachability itself rather than trusting the hint.
- **A short export no longer certifies itself as intact** — every integrity signal a dump carried (`:datom-count`, the semantic digest, the per-chunk SHA-256) was derived from the *write path*, so a dump that lost records agreed with itself perfectly and checking it against itself proved nothing. Measured: a 205-datom database exported short to 120 produced a manifest saying 120, a matching digest, `import-db {:verify? true}` → `:verified? true`, and `migrate/verify` → `:ok? true` — an operator restoring that backup was told everything was fine. `:stats` now also carries **`:source-datom-count`**, an independent witness counted from the database rather than from the stream, plus **`:transformed?`**, which says when a shortfall is *explained*: filtering a tenant out with `:xform` is a legitimately smaller dump, the same shortfall with no xform is loss. An unexplained shortfall is **refused** on import (`:import/incomplete-dump`, with the missing count), on both a filesystem dump and a konserve-store one; `{:allow-partial? true}` imports it anyway, and `{:count-source? false}` at export skips the extra count and records the source count as unknown.
- **`:checksums :skip` works on a konserve-store dump, not only a filesystem one** — the escape hatch for importing a dump whose chunk hashes do not verify was honoured by the manifest guard but not by the chunk reader, which checked unconditionally. Measured, the same damaged dump both ways: filesystem + `:checksums :skip` imported 20 datoms, store + `:checksums :skip` refused with `:import/checksum-failed`. It is the wrong way round — the hatch exists to salvage what is left of a damaged backup, and the store medium is the one an operator cannot open by hand to repair, as well as the only medium a browser has. The default is unchanged and still fails closed on both a missing and a mismatched hash on both media; only the explicit, warned-about opt-out passes. This is the third rule in this release written for one medium and not carried to the other (after the `:sha256` fail-closed rule and the incomplete-dump refusal), so the test added with it asserts PARITY over the damage × option matrix rather than each medium separately.
- **A ClojureScript throw that is not a `js/Error` no longer terminates the process mid-import** — `go-try-` expands to `(catch js/Error e e)` on ClojureScript, so `(throw #js {…})` or `(throw "oops")` escapes it; core.async then catches `js/Object`, closes the go block's channel, and **rethrows** onto the microtask queue, where nothing is listening. Measured on Node: the whole process exited mid-import with the bare object printed and no stack. Datahike now normalises such a throw into an `ex-info` (`:async/foreign-throw`, original value under `:thrown`) at the record-source `:read` seam — which is where a caller-supplied function runs, and therefore where a foreign throw is most likely. A foreign value thrown inside a callee's own go block still escapes into core.async before any caller can see it; that would require widening `go-try-`'s ClojureScript catch, which belongs to superv.async.
- **The public API's malli schemas are now enforceable, and seven of them were wrong** — `datahike.api.specification` has carried `[:=> …]` function schemas for every operation for a long time, but `emit-api` used them only to derive `:arglists` and `:doc`. They were never registered, so `malli.instrument/instrument!` had nothing to instrument, and the declared contract could drift from the real one with nothing to notice. It had: `datoms`, `seek-datoms` and `rseek-datoms` declared two `:function` branches that both accept two arguments, so malli took the arg-map one and the **documented** call `(d/datoms db :eavt)` was reported `:malli.core/invalid-input`; `as-of`, `since` and `gc-storage` referenced `types/time-point?` — a bare symbol where the registry key is `:datahike/time-point?` — and did not compile at all; and `with` declared two 2-arity branches (`:malli.core/duplicate-arities`) and did not compile either. Six of the seven are fixed. The seventh, `with`, is NOT: its two 2-arity branches ARE the Java binding's two overloads — `codegen/java` maps `STransactions` to `List` and `SWithArgs` to `Object`, and the `List` one marshals through `Util.normalizeCollections` — so merging them to satisfy malli deletes `with(Object, List)` from the generated source and the normalisation with it. The binding wins; `with` is excluded from instrumentation by name, in `datahike.api/uninstrumentable`, which a test pins as a set of exactly one. Since this specification also generates the Java API, the TypeScript definitions, the HTTP routes and the CLI, those were wrong in the generated bindings too, not only in the unenforced schema. All 47 registered schemas compile and pass under instrumentation, and the generated bindings are byte-identical to before the fix (verified by regenerating against a stashed copy — `java/src-generated/` is gitignored, so a `git diff` proves nothing) — the arity counts in a `:function` schema ARE the generated Java overloads, so the datoms family keeps two branches (one exactly-2-arity accepting either the index keyword or the arg-map, one three-or-more for components) rather than collapsing into a single variadic one, which would have emitted a single overload and stopped `Datahike.datoms(db, kwd(":eavt"))` from compiling.

  **Registration is not instrumentation.** `datahike.api/register-api-schemas!` runs at load and only records the schemas — no var is wrapped, nothing is validated, and there is no runtime cost, so a user who never opts in sees exactly the behaviour they always did (pinned by a test). What registration buys is that a user who already runs `(malli.instrument/instrument!)` in their own dev setup gets datahike's API checked too, for free, because `instrument!` instruments every registered schema. Datahike's own suite opts in the same way, in `datahike.test.malli-instrumentation-test`.
- **An import no longer blames the data for the store** — `:on-error :collect` exists to survive a bad *record* and name it, but it was applied to every failure, under a label (`:import/corrupt-datom`) that was a *fallback* rather than a judgement. Two things made that unavoidable. The error key never survived the writer boundary — a failure is wrapped twice, by `ExecutionException` (ex-data nil) and then by `superv.async/throw-if-exception-` reading *that* — so `(ex-data ex)` was empty even for a `:transact/unique` conflict that said exactly what was wrong, and the fallback was always what got recorded. And nothing asked whether a record could be responsible: measured, an `IOException` out of `writing/commit!` killed the writer, after which the narrowing retry attempted every remaining datom individually against a dead one and filed all **74** as `:import/corrupt-datom` — the first of them a `:db/txInstant` the *exporter* wrote — while `import-db` returned normally with 10 of 84 datoms restored. `datahike.tools/ex-error` now looks through the wrappers, so a collected error carries datahike's own key (`:transact/unique`, `:entity-id/missing`, …) and the datom it blames; and a failure outside the record-fault namespaces aborts with **`:import/apply-failed`**, the original exception as its cause, instead of being retried record by record and filed against data that did nothing wrong.
- **`:verified?` says which of its outcomes happened** — it is `true`/`false`/`nil`, and `nil` covered three unrelated situations (verification switched off, nothing to compare against, `:collect` swallowing the result), all of which read as "fine" in a report otherwise full of successes. Worse, the two import paths *disagreed* on one of them: given a source declaring no record count, the streaming path threw `:import/verify-failed` — "datom count mismatch", comparing the live count against `(- 0 dropped)`, a statement about nothing — while the index-build path returned **`:verified? true`**. Both measured. Verification is now decided in one place for both paths, and the report carries **`:verification`** `{:status :ok | :failed | :skipped | :unavailable, :expected, :actual, :missing, :reason}`. A source with no declared count is refused on both paths as `:import/verify-unavailable` (accurate, and still fail-closed) rather than certified by one and misdescribed by the other; a failed verification states its size, and under `:collect` `:missing` reconciles with the number of collected errors. `:verified?` keeps its old shape — deliberately not widened to a keyword, since a truthy `:not-checked` would make every `(if (:verified? rep) …)` read an unchecked import as a verified one.
- **`verify` and `estimate-import-memory` describe their own limits accurately** — both are synchronous and JVM-only, but both refused ClojureScript by calling `assert-sync-supported!` with a hardcoded `{:sync? true}`, so the message told the caller to "omit `:sync?` (the default here is false) and take from the returned channel". There is no `:sync?` to omit — it is a literal — and no channel; the advice described `export-db`/`import-db`, which really are `async+sync`. They now refuse by name (`:migrate/jvm-only`), and an explicit `{:sync? false}` is refused on the JVM too (`:migrate/sync-only`) instead of being silently ignored, so portable code fails the same way on both runtimes rather than working on one.
- **A failed chunk read is no longer an empty chunk** — `go-try-` turns an escaping Exception into a channel *value*, so `<?-` rethrows it; it does not cover a channel that **closes**, which is what a bare `go` that throws, a JVM `Error`, a ClojureScript throw of a non-`js/Error`, or a `>!` refusing nil all produce. `<?-` then yields `nil` — not an error, a value — and `(reduce rf acc nil)` is `acc`, so the chunk silently became empty. Measured on 20 datoms in 5 chunks with one read failing: `{:verify? false}` reported `{:datom-count 16, :verified? nil}` with 16 datoms in the restored database, and `{:on-error :collect}` reported `{:datom-count 16, :verified? false}` with no errors; the default did throw, but as a count *mismatch*, blaming an intact dump for the reader's failure. Every consumption site now names the failure (`:error :async/no-result`): both chunk reads on the import path, `verify`'s fold, and the batch report — where a nil carried no `:ex`, so the batch reported success, `progress` fired with its full count, and `:migration` became nil, restarting the id map and leaving dangling refs. The writer's forwarding of a background operation's result was the same bug with a worse ending: `(>! callback (<! res))` refused the nil, threw inside a bare `go`, and the caller's promise never resolved — **`d/gc-storage` hung** rather than failing.
- **`as-of` and `history` now agree with the current indices for same-transaction churn** — a value asserted and retracted within ONE transaction was reported by `as-of` as still asserted, contradicting the current indices, which correctly showed it absent. Both history entries carry the same `tx`, and the temporal fold sorted by `tx` alone; a stable sort preserves input order on ties, and that order comes from the temporal index where `added` sorts false before true, so the assertion always won. Assertions now fold before retractions within a transaction, making the retraction win on a tie — a temporal assertion and retraction sharing a `tx` can only mean the datom was created and removed inside that transaction. The opposite order is preserved: in retract-then-assert the re-assertion is the live datom, is not in the temporal index at all, and survives via a current-index probe confined to values the fold dropped because of a same-`tx` retraction (an ordinary retraction resolves without any lookup, and a history-heavy `as-of` scan showed no measurable change). The cardinality-one branch applies the rule per VALUE, so a transaction retracting one value and asserting another keeps the new one. **This changes query answers** for databases containing same-transaction assert+retract; other shapes are unaffected.
- **History no longer loses a retraction made in the same transaction as its assertion** — the temporal indices are ordered by `[e a v tx added]`, because an assertion and its retraction are distinct history entries that agree on the first four components when they share a transaction. `-temporal-insert` was passing the *current* comparator, `[e a v tx]`, under which those two datoms compare equal, so the second insert was a silent no-op and the retraction marker was dropped — `d/history` showed the fact as asserted and never retracted, contradicting the current indices, and because the temporal index is persisted the loss was durable. Only same-transaction assert+retract was affected (across transactions the entries differ in `tx`), ordering was never wrong (the current comparator is a strict prefix of the temporal one, so the two agree on every pair that is not a tie), and present-tense queries were correct throughout. An export reads the history view, so dumps taken from an affected database inherited the loss. Note this makes the stored history complete but does not by itself change how `as-of` folds it — see the following entry.
- **A transaction report now reflects what the transaction wrote** — two related defects, both from redundancy being resolved inside the index update rather than at the operation, as Datomic and DataScript both do.
  - *A re-assertion is now a no-op.* Transacting `[:db/add e a v]` for a value the entity already holds still wrote and reported it. Cardinality-one re-dated the fact to the new transaction — leaving the current index and history disagreeing about when it was asserted — while cardinality-many reported a datom that is in no index at all. Both are now complete no-ops: nothing is written, nothing is reported, and the datom keeps its original `tx`, matching Datomic and DataScript. This also fixes a schema-corruption wedge: `update-schema` `conj`s into the many-valued schema attributes, so re-transacting an identical entity spec grew `:db.entity/attrs` from `[:name]` to `[:name :name]` and the third such transaction was refused outright ([#457], reported since 0.2.1; the guard was dropped in the mid-2020 upsert refactor `e9d55972`).
  - *A cardinality-one supersession now reports its retraction.* Overwriting a cardinality-one value writes a retraction of the old value into history at that transaction, but reported only the assertion — so datahike's own history contradicted its own `:tx-data`, and a consumer could not undo the old value without separately knowing the attribute's cardinality. Datomic and DataScript both report the pair. **This adds one datom per cardinality-one overwrite to `:tx-data`**; consumers that count entries will see the difference.

  Redundancy is compared through the index's own datom comparator, so it is correct for `:db.type/bytes` and tuple values, where Clojure `=` compares byte arrays by identity. Attributes covered by a secondary index in valid-time (SCD2) mode are excluded from the no-op: the adapter builds each new version row from the assertions it receives in that transaction, so a restatement there is load-bearing rather than redundant. Retracting an absent value is unchanged. ([#457], [#894])
- **A superseded value no longer stays counted in `:hash` when nothing retains it** — `:hash` is an additive sum over datom hashes (`[e a v]` only, so it rolls monotonically forward as datoms are inserted and does not depend on the order they arrive in). With history kept, an overwritten or retracted value moves into the temporal index and stays counted, which is what makes an export/import round trip reproduce the value. Under `:keep-history? false` there is no temporal index, but `with-datom-upsert` still added the new value's term without subtracting the old one — so the sum named a value absent from every index and from any dump, and a database disagreed with a re-import of itself (`src 3737939373` vs `tgt 5253422115`; with history the two already agreed). The superseded term is now dropped exactly when nothing retains it, plus the equal-value case under both settings, where `-upsert` replaces a datom with the same `[e a v]` and `temporal-upsert` stores nothing at all. **History-keeping databases are unaffected** — their stored hashes do not change.
- **Form-analysis memoization + result-cache put threshold** — per-call work that is a pure function of the query FORM (normalization, connected-component analysis, clause-binding validation, `:in`-shape seeds, BigDecimal key checks) is memoized in a small LRU — a parameterized workload repeats one form with varying arguments and was re-running all of it every call (~25% of point-query dispatch). Keys are scale-sensitive for BigDecimal-bearing forms and never include argument values (map-form `:args` carry the database — keying on them would pin snapshots). `*result-cache-min-weight*` (default 0 = unchanged) lets callers skip caching tiny results where the insert costs more than recomputation. Also: queries whose `:in` bindings contain lookup refs now always take the relation path, the only one that restores the original lookup-ref value in projections. ([#935])
- **`*fold-scalar-ins*` — opt out of const-folding scalar `:in` bindings** — scalar `:in` values are normally folded into the query clauses as constants, which specializes the plan to the VALUE: a parameterized workload repeating one query shape with varying arguments misses the plan cache and replans per call. Binding `datahike.query/*fold-scalar-ins*` to `false` keeps scalars as input relations so one plan serves every argument. Default `true` — existing behavior unchanged. ([#932])
- **Query result cache: O(1) bucket weight** — the weighted-LRU accounted a bucket's weight by reducing over its whole entry map on every insert, so hot buckets made every cache put O(bucket size). The running total now lives in bucket metadata and updates incrementally; eviction order and weights are unchanged. ([#931])
- **Commits stay O(write-set) under a large query cache** — propagating a commit into the query result cache walked every cached bucket; a long-lived reader connection could make small writes pay for the whole cache. Buckets beyond a propagation threshold are dropped instead of walked, keeping commit cost bounded by the transaction's write set. ([#931])
- **Removing a schema entry checks 'attribute in use' on the RESULTING state** — a transaction that retracts the last datoms of an attribute and drops its schema entry in the same tx was rejected, because the in-use check ran against the pre-transaction database. The check now evaluates the state the transaction produces; dropping a schema entry while data still remains is rejected as before. ([#931])
- **Aggregates over a secondary index no longer ignore negation, filters and defaults** — the columnar secondary-index path pushes an aggregate straight into the index, and to do so it flattens the plan and reads each piece as a POSITIVE equality constraint on a column. Everything that negates, defaults, filters or re-sources a piece was therefore invisible to it. A folded negation carries an anti-marker and was read as an *equality*, so `(min ?s) (max ?s)` with `(not [?e :dept "eng"])` aggregated over exactly the rows the negation **excludes**; a range predicate folded into an indexed scan is neither a standalone predicate nor an attached one, so `[(> ?s 60000)]` was **dropped**; `:not-join` / `:or-join` / rule clauses were passed through as if they were column constraints; and a `get-else` lost its default. All silent, and all only reachable with a `:db.secondary/type` index declared — which is also why nothing caught them: **no database in the test suite declared one, so the path was exercised zero times**. The path now DECLINES any plan carrying meaning it does not implement and the query falls back to the ordinary aggregate paths, which handle all of it; plain and grouped aggregates keep using the index. The declining is a capability check, not a shape blacklist, so a future op attribute is refused by default rather than silently mis-executed. ([#926])
- **A multi-group query with a predicate on the joined side returns its columns in `:find` order again** — the fused path lets a consumer group emit WIDE tuples (all of its own variables) whenever that group carries an attached predicate or feeds a probe-map, and projects them back onto `:find` afterwards. The projection was gated on the plan carrying post-ops, but a predicate attached to the CONSUMER does not make one: the hoisting step harvests attached predicates from *producer* groups only. So nothing projected, and the raw wide tuple was returned — in the consumer's `(vec :output-vars)` **set-iteration order**. `[:find ?e ?en]` came back as `[?en ?e]`, and a `get-else` in that group widened it further, so a two-variable `:find` answered with **three-tuples**. Silent, and it needs no optional or aggregate machinery: two entity groups and one predicate on the joined side is the whole recipe. Because set-iteration order is a function of the variable symbols' hashes, the fault was **alpha-renaming sensitive** — `#{?e ?en}` iterates reversed while `#{?f ?fn}` does not — which is why a differential corpus with fixed variable names could never have found it, at any number of cases. The projection now runs whenever the emitted layout is not already the `:find` layout, and indexes tuples by the layout they actually have. ([#925])
- **`get-else` off a joined entity variable binds its default again instead of dropping the row** — `get-else` is total: an entity lacking the attribute contributes a row carrying the supplied default. That holds when the entity variable also carries an ordinary pattern (`[?e :name ?n] [(get-else $ ?e :nick "none") ?v]`), because the optional scan then fuses into that entity's group as an optional *merge*, which defaults on a lookup miss. But when the variable's **only** pattern is the `get-else` — it was bound by a sibling clause, `[?stmt :stmt/src ?si] [(get-else $ ?si :src/at ::absent) ?at]`, or by a *prior* `get-else` — the optional scan formed a group of its own, and the fused path joined that group to its producer by probing the consumer's scan field: an **inner** join, which silently dropped exactly the rows the default is for. No exception; the planner returned a strict subset of the relational engine's answer. A related shape was wrong on **both** engines: when *every* pattern on a variable is optional (two `get-else`s on the same entity), the group had no scan that may drive it, so whichever optional scan was chosen as the driver walked its own attribute's index — an entity lacking that attribute was never visited and its row vanished with *both* defaults. Standalone optional scans now stay off the fused path and run as the left-outer `bind-by-fn(get-else)` the relational engine already used for the `:in`-bound shape ([#884]), and an all-optional group is no longer assembled into an entity group at all. The rule that an optional scan may never *drive* a group's scan is now enforced on the one path that skipped it — a group admitting no valid scan/merge partitioning at all (two variable-attribute patterns) fell back to plain cost order — and asserted where fusability is decided. Queries whose `get-else` fuses as an optional merge, the common `[?e :name ?n] [(get-else $ ?e :nick "x") ?v]` shape, keep the fused path; the shapes that moved to the relational engine cost about 2.3x on a 20k-row measurement. ([#920], [#923])
- **A recursive rule whose self-call *transforms* a caller-supplied argument now computes its whole relation** — a head variable that no rule body binds takes its value from the call site (the pass-through mechanism), so the fixpoint's accumulator holds exactly the one value the caller passed. When a self-call passes a *different* value there — `(reachable ?head ?prev ?b2)` where `?b2` is `(dec ?budget)` — the lookup asked the accumulator for a value it was never filled with, so the recursion advanced **at most one level whatever the data**, and returned a silent subset. A budget/fuel-bounded traversal therefore returned only its starting point. Such a variable is now treated as **demand**: the call site supplies the first value, each lookup contributes the next, and the base cases are re-seeded per demanded value — the magic-set reading of a rule that is not range-restricted, and the only sound bottom-up evaluation of one, since its relation is infinite in that argument. Recursive-rule benchmarks got **faster** (demand is a pruning technique), and the fix applies on ClojureScript too. Where nothing bounds the constructed values — no comparison constrains the variable — no bottom-up evaluation can terminate, so the rule is handed to the relational engine, whose top-down search the data bounds; it answers such rules correctly. Both engines' rule evaluation is now also interruptible via `:cancel`, which neither was. ([#919])
- **ClojureScript: a recursive rule whose body has more than one clause returned a row of nils** — tuples reach the recursive-rule projection in two shapes: a one-clause branch body emits array tuples, while a body with *several* clauses takes the fused scan+merge path and builds vectors. The JVM projection dispatched on the shape; the ClojureScript one always used `aget`, which on a persistent vector is `undefined` rather than an error — so every head variable projected to `nil` and `(reaches ?a ?b)` answered `[[nil nil]]` instead of its relation. Silent, and on the engine that is the **default** in ClojureScript. The trigger is the clause count, not the encoding: a reified edge (`[?e :edge/from ?x] [?e :edge/to ?y]`) and two unrelated clauses fail identically, while the one-clause form was always correct — which is why it went unnoticed. Three sites shared the asymmetry, including the projection that fills the fixpoint's accumulator. ([#917])
- **`min`/`max` over a string attribute in a columnar secondary index return the value, not an internal code** — the Stratum columnar aggregate bridge dictionary-encodes string columns, and dictionary codes are assigned in first-seen order, so `(min ?dept)` over a `:stratum`-backed attribute answered with the code of the first value encountered — the wrong value *and* the wrong type (a double). Stratum now derives the lexicographic order at query time for exactly the columns a query aggregates, so the answer is the real extreme regardless of how the column was ingested (bulk, appended, or index-backed), and no column is refused for its encoding. `count`/`count-distinct` were always exact (the dictionary is a bijection) and are unchanged, as are all numeric aggregates. Requires stratum 0.3.77, which this pins. ([#916])
- **A recursive rule no longer inherits its caller's relations** — a rule's fixpoint computes the rule's whole relation independently of the call site (the caller joins on the output variables afterwards), but the evaluator kept any caller relation all of whose variables were head variables. On the recursive path a branch is renamed to the rule's **own declared** head variables — not to the call arguments, which may be constants — so those names are *internal*, and any caller variable spelled like one was captured as if it were the same variable. The call site need not even mention it: `[?x :sym "a"] (r ?p ?q)` against `[(r ?x ?y) …]` collides on the declaration's `?x`. Such a relation was hash-joined into the **base** branch, restricting the **accumulator** rather than merely the search, and that produced three different wrong answers from one mechanism: a right-recursive body looking up its second hop found the accumulator empty and the fixpoint stopped after one hop, returning a strict **subset** with no error (`a→b→c→d` gave `#{b}` instead of `#{b c d}`); a caller relation over **two** head-variable names joined the rule's whole relation against unrelated values so the rule returned **nothing**; and because a call's result relation is itself spelled with head-variable names, a **second call site** inherited the first call's answers — `(r ?x ?y) (s ?x ?b)` degenerated `s` into `r ⋈ s`. Renaming the caller's variables made the same queries correct, which is why this hid: existing rule tests happen to spell the caller differently or pass a ground argument. Branch bodies now start from an empty relation set, and — the plan-time half of the same capture — are no longer *planned* believing the outer scope's variables are bound either: a body whose function op referenced a head variable spelled like an outer one had that op cost-ordered ahead of the pattern that binds it, which the inherited relations used to mask. A branch is now planned believing only the head variables the call site actually supplies, so head variables a body cannot bind are still passed through as before ([#897]), and demand-restricting the accumulator remains available through magic-set propagation, which derives its demand from the rule rather than the caller. ([#911], [#915])
- **A repeated variable is now unified inside nested scopes and rule bodies** — `[?a :e ?a]` is a self-join wherever the clause sits, but normalisation reached only top-level `:where` patterns and plain `not` bodies. `not-join` / `or` / `or-join` bodies were excluded because the planner pushed an outer variable into the index bounds as a literal, so an injected equality made the negation stop excluding anything — a pre-existing fault, since fixed, which unblocks them. A rewritten `or` / `or-join` **branch** is kept as one form, because every element after the declared variable vector is a separate alternative and setting the equality beside the pattern would turn one conjunctive branch into two disjuncts; a plain `or` is promoted to `or-join` over the branch's original free variables, since every branch of an `or` must bind the same ones. **Rule bodies** matter most: rules arrive as the argument bound to `%` and never appear in `:where`, so normalising the query alone could not reach them — and it is the one scope where *both* engines answered wrongly, meaning no differential test could have flagged it. Rule *heads* are left alone; a repeated variable there constrains the caller's arguments. ([#913])
- **An entity group naming one attribute twice returns its rows again** — the sorted merge advances one cursor per *attribute*, in attribute order, so two clauses on the same attribute collapsed onto a single cursor and the group yielded nothing: `[?a :p ?x] [?a :p ?y] [?a :qq ?x]` over a `:db.cardinality/one` attribute answered `#{}`. Only card-one attributes reach that walk, which is why the shape looks fine with card-many. Such a group now takes the declaration-order per-cursor path, where every clause has its own cursor; groups without a repeated attribute keep the sorted walk. ([#913])
- **History queries: a clause sharing a variable with the scan is re-checked for every version** — the history fast path walks one forward cursor over the temporal index for the whole scan, so when an entity contributes several scan datoms — over `d/history` it always does, one per version — it materialized the second clause's matches into a replay buffer once and replayed them for the entity's remaining versions. The buffer is a function of the entity only, which is sound while the second clause is independent, but a clause sharing a variable with the scan clause has to be matched against the scan **datom**, and that changes from version to version. So the *first* version's matches were frozen and replayed for the rest: `[?e :a ?x ?t] [?e :b ?y ?t]` (shared transaction variable) lost every row belonging to a later transaction, and `[?e :a ?x ?t] [?e :b ?x ?u]` (shared value variable) *invented* rows pairing a value with the first version's transactions. Only history/as-of queries were affected — the current-db paths never replay — and the reference engine was correct throughout. The buffer now holds the entity's raw version list and re-applies the equality per scan datom whenever an obligation reads the scan datom; the common independent-clause join (`[?e :name ?n] [?e :age ?a]` over history) keeps the pre-filtered single-pass buffer unchanged. ([#913])
- **A predicate comparing two variables is no longer pushed into the index as a bound** — the pushdown analysis treated an already-bound variable as if it were a constant and wrote the *symbol itself* into the index bounds. An AVET slice from `?y` to `?y` matches nothing, so `[:find ?x :in $ [?y ...] :where [?x :e ?v] [(= ?y ?v)]]` returned **empty**; inside a negation the same mechanism made `(not-join [?a] [?a :e ?b] [(= ?a ?b)])` **stop excluding anything** and `(or-join [?a] (and [?a :e ?b] [(= ?a ?b)]))` match nothing; and with a range operator it **threw** `class clojure.lang.Symbol cannot be cast to class java.lang.Number`. Such a predicate is now declined for pushdown and evaluated normally. No optimization is lost: a variable bound to a single value is folded into the clause as a constant before planning, so `[(> ?s ?min)]` with a scalar `:in` binding still reaches the index — a variable that survives to the pushdown analysis holds a different value per row, which is precisely what an index bound cannot express. ([#912])
- **A variable repeated inside one clause is a self-join again** — `[?a :e ?a]` asks for entities that link to *themselves*, but every occurrence of a variable was treated as a slot to bind rather than, after the first, a constraint. Both engines answered wrongly and **differently**: the planner projected the entity position, the reference engine the value position (its variable map is built with `into`, so a repeated name collapses last-wins), which is why differential testing could never flag it — neither engine could serve as the other's oracle. Queries are now normalised before planning so a repeated occurrence becomes a fresh variable plus an explicit equality, at the single seam shared by `q`, `query-stats` and `explain`; a query with no repeated variable is returned unchanged (identical object), so plan and result caches are untouched. Applies to every position — entity/attribute/value/tx, four- and five-element patterns — and correctly leaves repeated arguments in function and predicate clauses alone, since `[(+ ?a ?a) ?y]` is not a self-join. Rule bodies and `not-join` / `or` / `or-join` bodies were excluded at first and are covered by the follow-up below. ([#912])
- **A variable shared by two merge clauses of one entity group is enforced** — the fused scan tested a merge's value against the *scan clause* only, so with `[?a :e ?b] [?a :f ?b] [?a :f ?c]` the two merges never compared their `?b` and the query returned rows where the two attributes hold different values. This was wrong on **every** planner path — direct, relation, columnar and pull — because they share the group scan, so it could not have been fixed by declining the fused path. The two booleans become an integer naming the binding slot each occurrence must equal, assigned in one left-to-right walk, so the first occurrence binds and every later one constrains, whether its partner is the scan or another merge; the common no-sharing case short-circuits on an integer compare and the hot loop stays allocation-free. The same change fixes a **column misalignment** on the relation path — a repeated value variable consumed a tuple slot but no output index, so every later column read one slot early and returned a *different attribute's value* — and a matching gap for transaction variables. ([#912])
- **Planner: a cyclic join between entity groups no longer drops the equalities it cannot enforce** — the fused direct path joins each consumer group to ONE producer group on ONE probe variable, so a query whose groups are connected by more than that had the surplus equalities silently discarded. `[:find ?a ?b :where [?a :e ?b] [?b :e ?a]]` (two groups sharing *two* variables) returned extra tuples, and `[:find ?a ?b ?c :where [?a :e ?b] [?b :e ?c] [?c :e ?a]]` (a group sharing variables with *two* earlier groups) additionally emitted a **nil column**, because the emitter found no source for the unjoined variable and filled in `[:const nil]`. The base engine always answered correctly. Worse, which of the two you hit depended on the **names of the variables**: the probe variable was `(first probe-vars)` off a hash-set, so `[?a :e ?x] [?a :f ?y] [?b :f ?x] [?b :e ?y]` took the fused path and answered wrongly while the same query spelled with `?u`/`?w` fell to the Relation engine and answered correctly — the 4-cycle was right for exactly half of 300 variable namings. Such plans are now declined up front and run on the Relation engine, which enforces every equality. The check is exact rather than a "looks cyclic" heuristic, so a producer feeding several consumers on distinct variables (the multi-consumer star) stays fused: a brute-force sweep of all 2- and 3-pattern queries over four variables and two ref attributes found that every plan it declines is one the fused path answered wrongly, so no correct query loses the fast path. ([#912])
- **Planner: a recursive rule that threads a caller-supplied parameter no longer throws** — a rule whose head takes a parameter its body never binds, e.g. `[(reachable ?anchor ?eps ?n) …base case, no ?eps…]` plus `[(reachable ?anchor ?eps ?o) … [(contains? ?eps ?ep)] (reachable ?anchor ?eps ?s)]` called with the edge set from `:in`, threw a `NullPointerException` from the fixpoint's dedup step (`rel-dedup-into!`) under the planner while the base engine answered correctly. `?eps` is not range-restricted, so its only possible value is the one the call site passed: the base engine gets that for free by renaming head vars to the **call args**, whereas the planner renames to the rule's own head vars (so a constant call-arg can be filtered after the fixpoint instead of restricting the accumulator) — leaving the parameter bound by nobody, the branch relation missing that column, and the dedup step dereferencing a `nil` index. The planner now marks, per branch, the head vars that branch's body cannot bind, and binds them at the call site from a constant argument, a `:in`-pinned value, or the outer relation's column — so the value reaches the body's own predicates too, not just the result tuple. When the caller has no binding either, the rule goes to the relational engine rather than inventing one. Recursive rules without such a parameter are untouched. Regressed when the planner became the default in 0.8.1705 ([#844]); reported with a minimal repro in [#897]. ([#899])
- **Planner: a `not-join` whose join vars come from `:in` no longer throws** — `(not-join [?s ?P] …)` with `?P` supplied as a scalar `:in` argument threw a `NullPointerException` out of the fused direct path. Scalar `:in` bindings are constants, not columns of the wide result tuple, so the anti-join post-filter found no slot for `?P` and cast a `nil` index; the base engine (and `DATAHIKE_QUERY_PLANNER=false`) always returned the right answer. The post-filter now takes such a join var's probe value from the constant map, and a join var that the fused path could not read at all — one bound by a function, which runs *after* the anti-join — makes the plan fall back to the Relation engine instead. A join var the negation never binds is also no longer keyed on (it constrains nothing, and keying on it silently matched no rows). Both sides of the anti-join are now checked up front: the sub-plan runs with no outer bindings, so it must *bind* every join var itself — one it merely reads, as `(not-join [?e ?a] [?e :color ?c] [(< ?a 25)])` reads `?a`, came back unbound, left the negation relation empty and silently excluded **nothing**. Those plans go to the Relation engine, which threads the outer context in. ([#905])
- **Planner: a negation that shares no variable with the rest of the query is a gate, not a Cartesian component** — `[?e :name ?n] (not-join [?age] [?e2 :age ?age])` with `?age` from `:in` raised `Query for unknown vars: [?e2]` under the planner; the base engine answers correctly (empty when the negation's body has a solution, a no-op when it has none). The Cartesian-split pass rooted the negation as its own component and then had to give that component's sub-query a `:find` var — but a negation *binds* nothing, so it could only offer a var local to its own body. Negations whose vars nothing in the query produces now attach to the primary component as global gates, a not-join's connectivity is its declared join vars only (its other vars are local to the negation, and a same-named var outside is a different var), and a component's `:vars` is restricted to what it can actually project. Relatedly, the planner's "insufficient bindings" check now counts scalar `:in` vars as bound, matching the base engine's `ctx-bound-vars` — it folds their values into the clauses but that fold never reaches a `not-join`'s declared var vector. The same scoping rule applies to **`or-join`**, which raised the identical error for a branch-local variable (`(or-join [?z] [?z :age ?local] [?z :color ?local])`) — only declared join vars correlate a sub-expression with the query around it. - **A negation whose variables are all `:in` constants constrains again** — supply every var a negation mentions through `:in` and the fold makes its body fully ground, turning the clause into a *boolean* over every row. A sync subscriber now also applies a commit in the order it was committed, rather than an order guessed back from key shapes. Requires konserve ≥ 0.9.356. *Experimental.* ([#875])
- **Streaming peer no longer exposes a db its indices don't back** — `connect-kabel` published a queryable db the moment the `:db` root arrived (cold path) or was found in the local cache (tiered shortcut); neither checked that the index NODES the root points at were actually present. The cold path was safe only by accident — konserve-sync ships nodes before the head — while the cached shortcut had **no node check at all**, so a peer reconnecting onto a partial cache (a root whose subtree an interrupted sync never finished writing) published a db whose first query walked into an absent node, tripping konserve's sync `-blob-exists?` on an async-only backend (browser, tiered memory+IndexedDB). Exposure now waits for konserve-sync's `:on-complete` — the handshake fully drained — for **both** paths, and the blind cached shortcut is gone; the cached root is merely a pre-fill, never a publish shortcut. The signal is exact: kabel acks a handshake batch only after applying every item in it, and the server sends `handshake-complete` only after that ack, so `:on-complete` arrives strictly after the last node *and* the head have landed. This needed a kabel fix to work at all — `subscribe!` accepted an `:on-handshake-complete` callback and silently dropped it, so the signal could never fire (kabel 0.3.100); a failed subscription now also raises instead of waiting forever on a handshake that will never come. Requires kabel ≥ 0.3.100. *Experimental.* ([#874])
- **Streaming reader's local cache now warms (tiered `:frontend-only`)** — a KabelWriter reader whose store is a tiered `{local, shared}` cache with `:write-policy :frontend-only` (e.g. `{lmdb, s3}` — a local LMDB node cache over the writer's shared S3, which the reader must never write) never populated its local frontend on live commits: konserve-sync's node push was subscribed on the *tiered* store, whose `:frontend-first` `exists?` check falls through to the shared backend — which already holds every content-addressed node — so every pushed node read as "already present" and was skipped, leaving the frontend permanently cold (served only by lazy read-through). The reader now subscribes konserve-sync to the frontend store directly, so streamed commit nodes land in — and existence is checked against — the local cache. Other tiered modes (write-through `{memory, indexeddb}`, where the backend *is* the local durable tier) are unchanged. Requires konserve ≥ 0.9.355 (the `:frontend-only` tiered write policy). *Experimental.* ([#873])
- **`gc-storage!` no longer NPEs on partially-swept lineage** — the mark phase destructured each commit record without a nil check, so a parent already removed by an earlier GC pass with a narrower window (or absent under `:commit-graph? false`) crashed the walk. Missing records now terminate that lineage cleanly. ([#869])
- **Fatal errors no longer hang transacts** — a fatal `Error` (assertion failure, OOM, …) inside the async write pipeline used to hang every in-flight and subsequent `transact` silently: the commit go-block only caught `Exception`, so an escaping `Error` killed the dispatch thread and left the writer parked forever on a silent channel; a dead transaction loop also left its queues open, accepting transacts whose callbacks could never fire. Now `commit!` converts fatal errors at the go boundary, a dying transaction loop closes its queues, and dispatching to a shut-down writer fails immediately with `:writer-shut-down`. Failure semantics are loud-and-safe: callers get the error, the writer shuts down, the store stays at the last good commit (the HEAD flip never happened). ([#867])
- **Commit crash on deep trees after reconnect (`NullPointerException` in `Branch.child`)** — reconnecting to a store and then mutating could leave an index's cached count unknown (persistent-sorted-set defers the subtree-count recomputation); the canonical root write handler then recomputed it on the storage-detached stored copy during the next commit, NPE-ing while materializing lazy children. Hit with deeper trees (small branching factor, or any large index whose SOFT-referenced children were collected under heap pressure) — the commit failed mid-write. Fixed upstream in persistent-sorted-set 0.4.132 (the root write handler serializes the cached count as-is — possibly "unknown" — and readers resolve it lazily with their own storage attached; this also covers ClojureScript, where storage is async). Guarded here by a seeded end-to-end regression test. Found by a diff-buf equivalence probe; pre-existing, independent of diff-buf. ([#867])
- **Query planner: variable-attribute cross-source Cartesian product** — a multi-source query with a variable-attribute pattern `[$b ?e ?a ?v]` (the attribute is a logic var — e.g. a join attribute retrieved from the data itself) whose value was produced by a function and reached through two or more linked entity-groups on the driving source was mis-ordered: the value-producing op ran *after* the variable-attribute scan, so the scan ran unconstrained and the cross-source join collapsed onto the non-selective attribute variable, yielding a Cartesian product. Such scans are now recognized as correlated joins and ordered after their attribute/value producers, so the join is selective. The legacy (relational) engine crashed outright on the same shape (`No matching clause: N` in `resolve-pattern-lookup-ref-at-index` — a relation-tuple position index exceeded the datom's five slots on a wide multi-source relation); such positions now resolve to the value unchanged. As a bonus, a variable-attribute scan whose attribute and value are both bound upstream now AVET point-seeks per `(attr, value)` pair instead of full-scanning — the dynamic-attribute join over a large target database drops from O(all datoms) to O(pairs · log n) (≈8000× on a 100k-datom benchmark). ([#865])
- **Query planner: as-of card-one merge skipped older visible values** — a date/tx `as-of` query whose timepoint fell between an attribute's initial and updated `:db/txInstant` could drop the older-but-still-visible card-one value (e.g. an entity's original `:age`): the fused merge found the current value, rejected it as too new, and stopped instead of looking back through temporal history. The merge now falls back to the assembled temporal slice. Surfaced by the native babashka-pod test suite; reproducible on JVM and JS. ([#863])
- **Query planner: `get-else` over `d/history` enumerated every version** — `[(get-else $ ?e :attr default) ?v]` is single-valued (the legacy engine returns one value or the default per entity), but on a `HistoricalDB` the planner forced the merge card-many and emitted one row per historical version (and, for card-many attributes, one row per value). `get-else` merges are now single-valued regardless of temporal type or attribute cardinality. ([#863])
- **Tiered store durability — silent data loss fixed** — writes through a tiered store with a memory frontend (the recommended config for browser/IndexedDB) could fail to persist index nodes to the durable backend. The memory frontend returns stored index roots by reference, so they carried the create-database connection's storage handle; a later connection then flushed new nodes into an orphaned buffer that commit never drained, leaving the backend with a root pointing at node blobs that were never written. In-process reads (served from the live frontend) masked it; the corruption surfaced as `Node not found in storage` on any cold read of the backend — process restart, a second peer, or dropping the frontend. Storage is now treated strictly as connection-scoped context: index roots are detached before entering the store and (re)bound to the reading connection on materialization (`datahike.index/with-storage`), so a flush always targets the connection's own storage regardless of how the value came back. Plain `:file`/`:memory` stores were unaffected. ([#854])
- **`commit-as-db` accepts a connection again** — `datahike.versioning/extract-store` detected connections via `instance? Connection`, which silently misfired when `deftype` recompilation (circular loads, REPL reloads) drifted the `Connection` class identity: a live connection fell through to the raw-store branch and `commit-as-db` threw a konserve `get-lock` NullPointerException instead of loading the commit. It now detects a connection via `IDeref`, matching the documented "connection, db value, or raw store" contract. ([#852])
- **Imports are now batched** — `datahike.migrate/import-db` now imports flat-files in configurable batches (`datahike.migrate/*import-batch-size*`, default `10000`) instead of one transaction. ([#845])
- **Query result cache bounded by size, not just snapshot count** — the attribute-dep-aware query result cache ([#795]) was an LRU capped only by DB-snapshot count (`*query-cache-size*`, default 64); each cached snapshot bucket can hold arbitrarily large result sets, so a handful of large queries could pin gigabytes of decoded tuples on the heap even though the snapshot-count cap never triggered. Adds a cumulative weight budget `*query-cache-weight-limit*` (default 1,000,000 result tuples; env `DATAHIKE_QUERY_CACHE_WEIGHT_LIMIT`; `set-query-cache-weight-limit!`; `0` disables) backed by a new size-aware `datahike.lru/weighted-lru` that evicts least-recently-used snapshots until the total is within budget, always retaining the most-recent snapshot. *Experimental.* (0.8, [#859])
- **Purge propagates to secondary indices** — `:db/purge` / `:db.purge/entity` / `:db.purge/attribute` / `:db.history.purge/before` now route a retraction event (`-transact` with `:added? false`) to every secondary index covering an affected attribute, the same way normal `:db/retract` does. Previously `with-temporal-datom` bypassed `update-secondary-indices` entirely, so purged datoms silently lingered in Scriptum (full-text), Proximum (vector), and Stratum (columnar) indices — a GDPR compliance gap. ([#832])
- **Query planner: stability fixes** — central `op-required-vars`; per-branch produced-vars in OR(-JOIN) bind contract; `not=` / `==` predicates pushed into AVET scan no longer silently dropped; NOT / predicate / or-join binding regressions; ctx-nil guard + nested form-args walker; CLJS-array tuple handling in `execute-pattern-scan` and `-collect`; rule bodies routed through the IR pipeline; function-only base cases in recursive rules; `:pushdown-preds` applied in temporal standalone pattern-scan. ([#813], [#814], [#815], [#816], [#818], [#819], [#821], [#825], [#826], [#827], [#806], [#807])
- **Query planner: temporal merge fast path** — a fully-unbound multi-attribute query over a history or as-of database (e.g. `[?e :name ?n] [?e :age ?a]` on `(d/history db)`) now drives the entity-group merge with a single forward cursor over the temporal index instead of one root-anchored seek per entity. On a 20k-entity history the `name + age` history join drops from ~65 ms to ~16 ms, with results bit-for-bit identical to the relational engine; Datahike now leads Datomic on all nine as-of/history shapes in the cross-database benchmark (see [query-engine.md](doc/query-engine.md#performance)). ([#844])
- **`d/explain` on temporal databases** — `explain` no longer throws when given a `HistoricalDB` / `AsOfDB` / `SinceDB` (the temporal wrappers carry no own indices); it now plans against the origin database's indices. ([#844])
- **Proximum secondary `-sec-flush` regression** — uses `IndexLifecycle/sync!` and surfaces the post-sync `:merkle-root` so the audit chain folds proximum nodes correctly; fixes NPE on every commit and stale commit-ids in the key-map. (0.8.1683, [#824])
- **`AsOfDB` / `SinceDB` reader swap** — `since-from-reader` was constructing `AsOfDB` and vice versa, causing silent incorrect behavior when deserializing `#datahike/AsOfDB` / `#datahike/SinceDB` tags via EDN or Transit (e.g. in the HTTP client). (0.8.1668, [#805])
- **Query cache: variable-in-attribute-position** — patterns like `[?e ?a ?v]` previously tagged cached entries with an incomplete dependency set, making them immune to invalidation; they now produce `:all` deps. (0.8.1667, [#804])
- **Missing-ident handling in `-ident-for`** — improved logic when an ident is missing; removes the prior warn-on-missing path. ([#800])
- **pydatahike: JSON Long coercion in transact** — JSON integers passed through transact are now coerced to Long correctly. ([#830])
- **pydatahike: tolerate cbor2 tag_hook signature variants** — works across cbor2 versions that vary the tag_hook callback signature. ([#829])

The improved api namespace is now the entry point to using Datahike and should be the only namespace that needs to be imported in your projects. However it is still possible to use other namespaces but there will be changes that might break existing behaviour. Please take a look at the [improved cljdoc documentation](https://cljdoc.org/d/io.replikativ/datahike/) for the api namespace.

With the change in the upsert implementation (#62), we expect up to 3x speedup in terms of transaction time. However, it also brings a breaking change to the content of transaction reports. In previous Datahike versions, following an upsert operation (which updates an existing entry), you would see in the :tx-data section of the transaction report both the old retracted datom and its newly added version. E.g.:

```clojure
#datahike.db.TxReport{
...
:tx-data [#datahike/Datom[1 :name "Ivan" 536870914 false]
          #datahike/Datom[1 :name "Petr" 536870914 true]]
...}
```

With this release, you would only see the newly added entry and no information about retraction or addition is shown (it is assumed to be an addition).

```clojure
#datahike.db.TxReport{
...
:tx-data [#datahike/Datom [1 :name "Petr" 536870914]]
...}
```
